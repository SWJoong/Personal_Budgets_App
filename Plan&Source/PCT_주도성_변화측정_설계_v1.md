# 사람중심생각(PCT) 관점 검토 — "주도성"과 "변화"를 담을 수 있는가

> **작성일**: 2026-07-25
> **선행 문서**: `온톨로지_사례관리_개편_검토보고서_v1.md`, `서식_이질성_해결방안_v1.md`
> **검토 대상**: `ontology/pcp_ontology.rdf` (3차 시점, 클래스 23 / 관계 32)
> **검토 요청**: 아름드리꿈터 시범사업의 두 핵심 질문에 이 구조가 답할 수 있는가

---

## 0. 검토의 기준선 — 아름드리꿈터 시범사업의 실제 흐름

```
PCD 회의 (당사자와 함께 알아가기)
   ↓
SIS-A 지원요구 사정
   ↓
개별지원계획(ISP) 수립 — 당사자가 지역에서 자기 삶을 살아가도록
   ↓
연 150만원 개인예산 편성 · 집행
```

이 시스템에서 중점적으로 보아야 할 것은 두 가지입니다.

1. **개인예산 사용 과정에서 당사자가 얼마나 주도적으로 계획을 세우고 실행했는가**
2. **그 과정에서 지역사회와의 관계나 개인에게 어떤 변화가 있었는가**

그리고 이 전 과정에 **사람중심생각(PCT)** 이 반영되어야 합니다.

---

## 1. 검토 결론

**두 질문 모두 검토 시점의 구조로는 답할 수 없었습니다.**

현재 온톨로지는 **한 시점의 사진(static snapshot)** 이었고, 요구되는 것은 **변화의 기록**입니다.
PCT의 핵심인 순환 — 알아가기 → 계획 → 실행 → 배움 → 다시 알아가기 — 에서
**앞의 절반만 있고 뒤의 절반이 없었습니다.**

| 질문 | 검토 시점 | 이유 |
|---|:---:|---|
| 주도적으로 **계획**을 세웠는가 | **✕** | `당사자 → 예산 계획` 관계 자체가 없음 |
| 주도적으로 **집행**했는가 | **✕** | 거래의 결정 주체를 구분하는 속성 없음 |
| **지역사회 관계**에 변화가 있었는가 | **△** | 관계 지도 4분면은 있으나 시점 비교 불가 |
| **개인**에게 변화가 있었는가 | **✕** | 평가·성과 노드 자체가 없음 |

## 2. 발견된 결함 8건

### 결함 1 — 당사자가 자기 계획의 저자가 아니었다 ★ 가장 심각

관계 32개를 전수 확인한 결과 **`Person → BudgetPlan` 관계가 아예 없었습니다.**
계획과 이어진 것은 이 셋뿐이었습니다.

| 기존 관계 | 방향 |
|---|---|
| 지원자 → 당사자 | 계획 수립을 지원한다 |
| 가치·욕구 → 계획 | 계획에 반영된다 |
| 강점 → 계획 | 강점이 계획을 뒷받침한다 |

즉 그림상 계획은 **"가치에서 파생되고 지원자가 지원하는 것"** 이지
**"당사자가 만드는 것"이 아니었습니다.**

개인예산제의 철학 자체가 데이터 구조에서 빠져 있었던 것이며,
1차 보고서가 인용한 리서치의 경고 — *"ISP가 당사자의 주도적 삶을 그려내기보다
복지관에 이미 존재하는 서비스를 끼워 맞추는 공급자 중심의 시혜적 산출물로 전락할 위험"* —
을 **제가 만든 온톨로지가 그대로 재현**하고 있었습니다.

### 결함 2 — 주도성을 측정할 속성이 없었다

`당사자 → 집행 내역` 관계의 라벨은 "지출을 결정한다"였지만,
**실제로 누가 결정했는지 구분하는 속성이 없었습니다.** 모든 거래가 동일하게
"당사자가 결정한 것"으로 보였습니다 — 라벨이 사실을 앞서간 것입니다.
`transactions.creator_id`는 "누가 입력했나"이지 "누가 결정했나"가 아닙니다.

### 결함 3 — SIS-A가 온톨로지에 없었다

시범사업 흐름의 명시적 단계인데 클래스 목록에 없었습니다.
**기존 DB에는 `sis_assessments` 테이블이 이미 있습니다**(6개 하위척도 원점수·표준점수,
총 표준점수, 지수, 백분위). ISP 수립의 객관적 근거인데 그래프에서 빠져
**"왜 이 계획인가"의 근거 사슬이 끊겨** 있었습니다.

### 결함 4 — 평가·성과가 없었다

`evaluations`(월별 4+1)와 `goal_evaluations`(목표별 4+1 + 목표치/실적)가
**DB에는 있으나 온톨로지에 없었습니다.**
"개인에게 어떤 변화가 있었는가"를 담을 곳이 그래프에 존재하지 않았습니다.

### 결함 5 — 시간 개념이 없었다

모든 노드가 정적이었습니다. `ValueNode.status`와 `NetworkEntity.lastContactDate`는 있었으나
**T1 시점과 T2 시점을 비교할 구조가 없었습니다.**
"관계가 늘었나 줄었나", "3월 대비 12월에 무엇이 달라졌나"를 답할 수 없었습니다.

### 결함 6 — PCD 회의(과정)가 노드로 없었다

"PCD를 당사자와 함께 **회의하며** 알아간다"에서, 산출물(가치·욕구)만 있고
**그것이 도출된 회의와 참여자가 없었습니다.**
PCD는 당사자를 잘 아는 주변 사람들이 함께 모여 하는 것인데 누가 함께했는지가 남지 않았고,
당사자가 그 회의에 있었는지 여부 자체가 주도성의 1차 지표인데 담을 곳이 없었습니다.

### 결함 7 — To/For 균형이 그래프에 안 보였다

균형은 SQL 뷰(`v_to_for_balance`)로만 존재했습니다. 그래프에는
`당사자 → 나에게 중요한 것`, `당사자 → 나를 위해 중요한 것` 두 화살표가 있을 뿐
**"균형"이라는 개념 자체가 시각화되지 않았습니다.**

### 결함 8 — 월별 계획이 온톨로지에 없었다

기존 앱의 핵심 테이블(`monthly_plans`)인데 누락되어
**연간 ISP → 월 실행 계획 → 집행**의 사슬이 끊겨 있었습니다.

## 3. PCT 도구 반영도 (검토 시점)

| PCT 도구 | 반영 |
|---|:---:|
| 중요한 것 To / For | ◯ |
| 소통 차트 | ◯ |
| 잘 맞는 지원 / 피해야 할 것 | ◯ |
| 관계 지도 | ◯ |
| **4+1 질문** (시도·배움·만족·불만족·향후) | **✕** |
| **배움 기록 (Learning Log)** | **✕** |
| 좋은 하루 / 나쁜 하루 | ✕ |
| 도넛 (책임의 범위) | ✕ |
| 매칭 (지원자–당사자 궁합) | ✕ |

**4+1과 배움 기록의 부재가 결정적이었습니다.** 이 둘이 PCT에서
"실행에서 배운 것이 다시 앎으로 돌아오는 고리"를 담당하는데, 없으므로
순환이 끊기고 변화를 볼 수 없었습니다.

## 4. 보완 설계

### 4.1 목표 — 순환 고리를 닫는다

```
        ┌──────────────── 평가에서 새로 알게 된 것 ─────────────────┐
        ↓                                                          │
  PCD 회의 → 가치·욕구 → 연간 ISP → 월별 계획 → 집행 → 월별 평가(4+1)
     ↑                      ↑
  SIS-A 사정 ───────────────┘ (근거)
```

### 4.2 신규 클래스 6개

| 클래스 | 역할 | 대응 테이블 |
|---|---|---|
| **사람중심 회의** `PlanningMeeting` | PCD·PATH·계획수립·평가회. 과정 자체를 기록 | 신규 `planning_meetings` |
| **지원요구 사정** `SupportNeedsAssessment` | SIS-A. ISP의 객관적 근거 | **기존 `sis_assessments`** |
| **월별 계획** `MonthlyPlan` | 연간 ISP → 월 실행 사슬 | **기존 `monthly_plans`** |
| **월별 평가** `Evaluation` | 4+1 질문 | **기존 `evaluations`** |
| **성과 스냅샷** `OutcomeSnapshot` | 시점별 지표 = 변화 측정의 실체 | 신규 `outcome_snapshots` |
| **관계 지도 4분면** (3차에서 추가됨) | 가족·친구·유급지원자·지역사회 | 신규 `network_entities` |

### 4.3 주도성 — 질문 ①에 답하는 구조

**당사자를 계획의 저자로 명시하는 관계 4개를 신설했습니다.**

| 신규 관계 | 의미 |
|---|---|
| **`당사자 → 계획을 세운다 → 예산 계획·ISP`** | ★ 계획은 당사자에게 주어지는 것이 아니라 당사자가 만드는 것 |
| `당사자 → 이번 달 계획을 세운다 → 월별 계획` | 월 단위 주도성 |
| `당사자 → 회의에 참여한다 → 사람중심 회의` | 참여 자체가 주도성 1차 지표 |
| `당사자 → 스스로 돌아본다 → 월별 평가` | 평가가 당사자에 '대해' 쓰이는 것이 아니라 당사자가 '하는' 것이 되게 함 |

기존 `지원자 → 계획 수립을 지원한다 → 당사자`는 그대로 둡니다.
**계획의 주인은 당사자이고 지원자는 곁에서 돕는 사람**이라는 구분이 두 관계의 차이입니다.

**주도성 기록 방식 — 자동 추정 + 보정** *(현장 부담을 고려해 확정)*

`transactions.decided_by` 4단계:

| 값 | 의미 |
|---|---|
| `self` | 당사자가 스스로 정함 |
| `self_with_support` | 당사자가 정하고 곁에서 도움받음 |
| `suggested_accepted` | 지원자가 제안하고 당사자가 선택함 |
| `supporter` | 지원자가 결정함 |

- **당사자 화면에서 등록된 거래(`creator_id = participant_id`)는 `self`로 자동 추정**
- 그 외는 NULL로 두고, 실무자가 **영수증 검토 대기열에서 필요할 때만 한 번 클릭**으로 지정
- NULL은 "아직 확인 안 함"이며 비율 계산에서 **분모에는 들어가되 분자에는 안 들어갑니다** —
  모르는 것을 주도적이었다고 세지 않습니다
- 매 거래 4단계 선택을 강요하지 않는 이유: 리서치 7.2(실무자 소진 예방)와 충돌하기 때문

계획 단계는 `care_plans.self_direction_level`(participant_led / co_produced / supporter_led)로
기록합니다. 저자는 언제나 당사자이지만 실제 주도 수준은 별개이며,
해가 갈수록 `participant_led`로 옮겨가는 것이 사업의 목표입니다.

### 4.4 과정과 근거 — 결함 3·6·8 해소

| 신규 관계 | 의미 |
|---|---|
| `지원자 → 회의를 진행한다 → 사람중심 회의` | 지원자는 퍼실리테이터 (결정자가 아님) |
| `지역사회 관계망 → 회의에 함께한다 → 사람중심 회의` | 누가 이 사람의 삶을 함께 그렸는가. 유급 지원자만 앉아 있는 회의는 그 자체가 신호 |
| `사람중심 회의 → 이 회의에서 알게 되었다 → 가치·욕구` | "언제부터 이렇게 알고 있었나"를 되짚을 수 있음 |
| `당사자 → 지원요구를 사정받는다 → SIS-A` | PCD가 "무엇을 원하는가"라면 SIS-A는 "어디에 얼마나 지원이 필요한가" |
| `SIS-A → 이 영역에 지원이 필요하다 → 분류 용어` | 어휘 계층 경유 → 복지부 8대분류로도 환산 가능 |
| `SIS-A → 계획의 근거가 된다 → 예산 계획` | 이 화살표가 없으면 계획이 사정과 무관하게 세워졌다는 뜻 |
| `예산 계획 → 월별 계획으로 나뉜다 → 월별 계획` | 연간 → 월 실행 |
| `월별 계획 → 이렇게 실행되었다 → 집행 내역` | 계획 대비 실제 |

회의에는 `participant_attended`(참석 여부)와 `participant_role`(led / spoke / present / absent)을
기록합니다 — **참석했다고 다 같은 참여가 아니기 때문**입니다.

### 4.5 순환 고리 — 질문 ②에 답하는 구조 ★ 핵심

| 신규 관계 | 의미 |
|---|---|
| `월별 평가 → 계획이 어떻게 되었는지 본다 → 월별 계획` | 4+1의 "시도한 것" |
| **`월별 평가 → 평가에서 새로 알게 되었다 → 가치·욕구`** | ★ **이 화살표가 순환을 닫습니다** |
| `월별 평가 → 그 시점의 지표를 남긴다 → 성과 스냅샷` | 변화의 기록 |
| `당사자 → 시점별 성과 기록을 가진다 → 성과 스냅샷` | 시계열 |

**순환을 닫는 화살표에 대하여.** 4+1의 "배운 것"이 새로운 가치·욕구 노드가 되어
다음 계획의 입력이 됩니다. 예를 들어 *"수영은 좋아하는데 사람 많은 시간은 힘들어한다"* 는 배움은
새로운 `좋은 지원 / 피해야 할 것` 노드가 되고, 다음 달 계획에 반영됩니다.
사람중심생각의 **배움 기록(Learning Log)** 이 하는 일이며,
**이 고리가 없으면 평가는 서류로 끝나고 당사자에 대한 앎은 갱신되지 않습니다.**

실무 흐름: 월별 평가의 "배운 것"을 실무자가 읽고 →
"새로 알게 된 것을 프로필에 추가할까요?" 버튼 → 가치 노드 생성(`source='evaluation_learning'`).

### 4.6 성과 스냅샷 — 변화 측정의 실체

**월별 평가 시점에 자동 계산·저장** *(추가 입력 없음, 현장 부담 고려해 확정)*

| 지표 | 내용 |
|---|---|
| `balance_index` | To/For 균형 −1(전부 For) ~ +1(전부 To) |
| `to_count` / `for_count` | 가치 노드 수 |
| `family/friend/paid/community_count` | 관계 지도 4분면 인원 |
| `unpaid_ratio` | 무급 관계 비율 |
| `self_directed_ratio` | 주도성 = 당사자 주도 지출액 / 전체 집행액 |
| `distinct_resource_count` | 그 달에 방문한 서로 다른 자원 수 (생활 반경) |

> **뷰가 아니라 테이블로 저장하는 이유**: 과거 시점의 지표는 그때의 데이터로 고정되어야 합니다.
> 나중에 관계망을 정리하거나 가치를 보관 처리해도 3월 스냅샷은 3월의 값이어야 추이가 의미를 갖습니다.

이로써 To/For 균형이 SQL 뷰에만 있던 것에서 **그래프의 노드 속성**으로 올라옵니다(결함 7 해소).

성과 보고에 그대로 쓰이는 질의:
```sql
SELECT snapshot_month, friend_count, unpaid_ratio, self_directed_ratio, balance_index
FROM outcome_snapshots WHERE participant_id = ? ORDER BY snapshot_month;
```
→ *"3월 대비 12월에 친구가 2명 늘었고, 주도성 비율이 0.3에서 0.7이 되었다"*

## 5. 보완 후 답변 가능성

## 6. 이 설계가 지키려는 원칙

1. **숫자는 실무자용 진단 도구이지 당사자를 평가하는 점수가 아니다.**
   당사자 화면에는 주도성 비율·균형 지수를 숫자로 보여주지 않습니다.
   '나의 그림'과 *"지난달보다 새로운 곳에 2번 더 다녀왔어요"* 같은 서술로만 표시합니다.

2. **모르는 것을 좋게 세지 않는다.** `decided_by`가 NULL인 거래는 주도성 비율의
   분자에 들어가지 않습니다. 기록이 없으면 없는 것으로 둡니다.

3. **실무자에게 새 입력을 최소한만 요구한다.** 신규 입력은 회의 기록과
   관계망 등록 두 가지이며, 주도성과 성과 지표는 자동 추정·자동 계산입니다.

4. **지원자는 퍼실리테이터다.** `회의를 진행한다`·`계획 수립을 지원한다`는 있어도
   `계획을 세운다`는 당사자에게만 있습니다.

### `#ServiceDomain`을 새 클래스로 만들지 않은 이유

보고서는 정부 지출 허용 영역(주거환경·일상생활·보건의료 등)을 고정 클래스로 제안했습니다.
그러나 지출 영역 구분은 **사업마다 다릅니다** — 복지부 8영역, 경기 기회소득 5영역,
기관 자체 분류가 공존하며 앞으로도 제도가 바뀔 때마다 달라집니다.
`서식_이질성_해결방안_v1.md`에서 이미 이 문제를 다루었고, 해법은
**복수 분류체계를 등록하고 crosswalk로 상호 매핑**하는 어휘 계층이었습니다.

따라서 새 클래스 대신 **복지부 지출 영역을 하나의 taxonomy로 시드**하고
`BudgetItem → 지출 영역으로 분류된다 → TaxonomyTerm` 관계를 걸었습니다.
보고서가 원한 정책 효과성 거시 분석("어떤 장애 유형이 어느 영역에 예산을 많이 썼는가")은
그대로 가능하며, 사업이 바뀌어도 스키마를 고칠 필요가 없습니다.

### 채택한 제안 — 실제로 없었던 것들

보고서의 지적 중 **행정·재무 거버넌스 부재는 정확했습니다.** 다음을 추가했습니다.

**신규 클래스 3개**

| **예산 세목** `BudgetItem` | 심의·승인·정산이 실제로 이루어지는 최소 단위. 계획 전체가 아니라 **항목마다** 승인·조건부·반려가 갈린다. 기존 `budget_line_items` 테이블이 있었으나 온톨로지에는 없었다 |

근거 없는 지출을 구조가 드러내는 것까지는 맞지만, 자동 기각으로 이어지면

실무자만 대신 넣을 수 있다면 그것은 권리 구제가 아니기 때문입니다.
