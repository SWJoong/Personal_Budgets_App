## 1. 문제 정의

### 1.1 같은 제도, 전혀 다른 서식

현재 저장소에 실물 양식이 있는 두 사업과 기관 자체 ISP를 나란히 놓으면 구조가 거의 겹치지 않습니다.

| | **보건복지부형** | **서울형** | **아름드리 자체 ISP** |
|---|---|---|---|
| 분량 | 5개 장, 매우 상세 | 2개 장, 경량 | 7개 장 |
| 인적사항 | 신청인·대리인·가족표·환급계좌·거주형태·가구특성·보장구 | 접수번호·중도장애 발생시기·공공부조·중복참여 여부 | 이름·생년월일·장애유형·주지원자 |
| 욕구 도출 | "현재 일상생활" 자유질문 5개 **+ 8대분류×중분류 매트릭스** | "나의 상황" 자유질문 5개 **(재능·강점 포함)** + 원하는 서비스 3개 | **SIS-A 8영역** + To/For 순위 |
| 예산 표현 | 차감 이용비율(10/15/20%) + 서비스계획 **11컬럼 표** | 없음 (신청 단계) | 관·항·목·세목 + 산출내역 |
| 평가 | — | — | 4+1 평가 |
| 서식 고유 요소 | 활동지원 신체:가사:사회 비율, 만족도 5점 척도 | **개인정보 동의서·서명이 서식의 일부** | 삶의 균형 "(To)와(For)" 컬럼 |

### 1.2 지원영역 분류체계가 4종이며 서로 호환되지 않음

| 분류체계 | 영역 |
|---|---|
| 보건복지부 8대분류 | 신체적 건강 / 정신적 건강 / 주거 / 일상생활 / 일자리 / 법률 및 권익보장 / 문화 및 여가 / 바우처 유연화 |
| SIS-A 8영역 (아름드리) | 고용 / 평생학습 / 가정생활 / 건강 및 안전 / 사회 / 지역사회생활 / 보호 및 권리주장 / 행동 지원요구 |
| 경기 기회소득 5영역 | 운동 / 문화·여가 / 교육·봉사 등 |
| 서울형 | 분류 없음 (자유 서술) |

현재 스키마는 `support_goals.support_area`가 **자유 텍스트**입니다. 기존 설계 제안서에서도
"지원 영역 코드화 — 초기 A(자유 텍스트), v4.0에서 enum 도입"으로 **이미 유예된 결정**이었고,
이 문서가 그 결정을 해소합니다.

여기에 더해 사람중심실천 도구 자체도 기관마다 다릅니다 — PATH(꿈 찾기), 한 장 소개서(OPD),
삶의 그림(POL), Essential Lifestyle Planning, 4+1 평가. 산출물의 모양이 전부 다릅니다.

### 1.3 그러나 — 공통 의미소는 존재합니다

세 양식을 질문 단위로 분해하면 **표현만 다를 뿐 같은 것을 묻고 있습니다.**

| 공통 의미 | 보건복지부형 | 서울형 | 아름드리 ISP |
|---|---|---|---|
| 원하는 삶 | "내 삶에서 가장 원하는 것은?" | "내가 원하는 삶의 모습" | "나에게 중요한 것" |
| 필요한 지원 | "변화를 위해 필요한 지원은?" | "내가 원하는 변화와 지원" | "나를 위해 중요한 것" |
| 강점·재능 | — | **"나의 재능, 강점, 기술"** | (SIS-A 강점 기반) |
| 중요한 사람 | "가장 자주 만나는 사람은?" | — | 주 지원자 |
| 어려움·장벽 | "가장 불편한 점은?" | "장애로 인한 사회적 제한" | — |
| 목표 | 5절 "목표" | "시도하고 싶은 것(1~2년)" | 성과 및 산출 목표 |
| 서비스·예산 | 서비스계획 11컬럼 표 | 지원받고 싶은 서비스 3개 | 관·항·목·세목 |

**결론: 이 이질성은 온톨로지를 부정하는 근거가 아니라 온톨로지가 필요한 이유입니다.**
의미 계층이 있으면 서식은 그 위의 투영(projection)이 됩니다. 의미 계층 없이 서식 단위로 앱을 만들면,
기관이 하나 늘 때마다 코드가 한 벌씩 늘어납니다.

## 2. 현행 코드 진단

### 2.1 서식 시스템이 둘로 갈라져 있고 추상화 수준이 정반대

| 축 | 추상화 | 저장 방식 | 새 서식 추가 비용 |
|---|:---:|---|---|
| **월별 평가 서식** (`evaluations`) | ★★★☆☆ | `evaluation_template` TEXT + `template_data` JSONB | 5개 파일 수정 |
| **연간 이용계획서 서식** (`care_plans`) | ★☆☆☆☆ | `plan_type` TEXT + `content` JSONB | **13개 지점 + 신규 컴포넌트 약 200줄** |

**평가 서식은 이미 옳은 방향으로 절반쯤 와 있습니다.** `src/types/eval-templates.ts`가
`EvalField{id, label, placeholder, rows}[]` 배열로 서식을 모델링하고,
`resolveTemplateFields()` 단일 해석 함수를 모든 경로(폼 렌더링·저장·AI 프롬프트)가 경유합니다.
`EvaluationForm.tsx`는 `fields.map()`으로 렌더링할 뿐 서식별 분기가 **0건**입니다.

**이용계획서는 정반대입니다.** `src/types/care-plans.ts`에는 필드 메타데이터 개념이 아예 없고,
서식마다 전용 TypeScript 인터페이스(`MohwPlanContent`, `SeoulPlanContent`)와 전용 React 컴포넌트
(`MohwPlanFormInner`, `SeoulPlanFormInner`)가 하나씩 대응합니다. `content` JSONB는 스키마 유연성이 아니라
**서로 다른 두 고정 구조를 한 테이블에 담기 위한 union 저장소**로 쓰이고 있습니다.

절 번호("2", "3", "4", "5")와 제목("현재 이용서비스 현황" 등)이 JSX 문자열 리터럴이고,
서비스계획 표는 `grid-cols-12`에 `col-span-2/4/3/2/1`로 **컬럼 폭까지 하드코딩**되어 있습니다.

### 2.2 DB는 이미 유연합니다 — 병목은 100% 프론트엔드

`plan_type`과 `evaluation_template` 모두 **CHECK 제약도 ENUM도 없는 TEXT**입니다.
허용값은 주석과 TS 타입에만 존재합니다. 즉 **새 서식 추가에 DB 마이그레이션이 필요 없습니다.**
막고 있는 것은 전적으로 애플리케이션 코드입니다.

### 2.3 확장 이전에 반드시 고쳐야 할 결함 6건

조사 중 발견된 실제 결함입니다. 서식을 늘리기 전에 해소해야 합니다 —
지금 상태로 서식을 추가하면 결함이 그대로 증폭됩니다.

### 2.4 이용계획서에는 인쇄·출력 경로가 아예 없습니다

앱 전체에서 인쇄 스타일을 갖춘 페이지는 월간 예산 보고서 한 곳뿐이고, 그 보고서는 거래·재원만 출력할 뿐
이용계획서나 평가를 참조하지 않습니다. **`care-plans/[participantId]/[planType]` 라우트는 출력이 아니라 편집 폼입니다.**

이는 실무자가 **앱에 입력한 뒤 제출용 서식을 한글·워드로 다시 작성하고 있을 가능성이 높다**는 뜻이며,
"한 번 입력, 여러 양식 출력"의 실무 가치가 예상보다 크다는 근거가 됩니다.

### 2.5 현행 자체 서식(custom)의 제약

관리자가 런타임에 정의할 수 있는 서식은 하나뿐이고, 그마저도
**기관 전체에 단 1벌 · 최대 6항목 · 자유서술 textarea만** 지원합니다.
체크박스·라디오·표·매트릭스·섹션 구분이 불가능하므로, 복지부형의 8대분류 매트릭스,
서비스계획 11컬럼 표, 서울형 동의서 서명은 애초에 표현할 수 없습니다.

## 3. 해결 원칙

> **서식을 통일하지 않는다. 의미를 통일하고, 서식은 그 위의 투영으로 만든다.**

세 가지 이유로 "통합 서식 하나 만들기"는 답이 될 수 없습니다.

1. **법정 서식은 임의 변경 불가.** 복지부에 제출하는 문서는 복지부 양식 그대로여야 합니다.
2. **기관의 실천 정체성.** 서식은 그 기관이 사람을 어떻게 보는지를 담습니다.
   서울형이 "재능·강점"을 먼저 묻는 것은 강점 기반 실천의 선언입니다. 통합은 이 차이를 지웁니다.
3. **제도는 계속 바뀝니다.** 2026년 본사업 지침이 확정되면 서식이 또 바뀝니다.
   서식이 코드에 박혀 있으면 제도 변경마다 배포가 필요합니다.

이 접근은 보건의료 정보학에서 검증된 패턴입니다 —
**openEHR의 2-level modeling**(변하지 않는 Reference Model + 임상 현장이 정의하는 Archetype),
**FHIR의 Questionnaire + Profile**(서식 정의와 의미 자원의 분리)이 같은 문제를 같은 방식으로 풉니다.

## 4. 3계층 설계

```
┌─────────────────────────────────────────────────────────────┐
│ 계층 3  서식 (기관·사업별, 데이터)                            │
│  form_definitions(JSON) + form_responses(extras)            │
│  → 렌더러는 단 1개. 새 서식 = JSON 1건. 컴포넌트 개발 불필요   │
├─────────────────────────────────────────────────────────────┤
│ 계층 2  어휘 (매핑 가능)                                      │
│  taxonomies / taxonomy_terms / term_mappings                │
│  → 복지부8·SIS-A8·경기5를 각각 등록하고 상호 매핑(crosswalk)   │
├─────────────────────────────────────────────────────────────┤
│ 계층 1  의미 (기관 무관, 불변)                                │
│  value_nodes / support_goals / budget_line_items /          │
│  transactions / service_resources / network_entities        │
│  → 어느 기관·어느 사업이든 동일. 그래프·룰엔진·AI가 읽는 층    │
└─────────────────────────────────────────────────────────────┘
```

### 4.1 계층 1 — 의미 계층: `value_nodes.kind`를 2종에서 8종으로

1차 보고서는 `kind`를 `important_to` / `important_for` 2종으로 설계했습니다.
**세 양식을 실제로 매핑해 보니 부족합니다** — 서울형의 "재능·강점"이 착지할 곳이 없습니다.

| kind | 착지하는 서식 질문 |
|---|---|
| `important_to` | 복지부 "내 삶에서 가장 원하는 것", 아름드리 "나에게 중요한 것" |
| `important_for` | 복지부 "변화를 위해 필요한 지원", 아름드리 "나를 위해 중요한 것" |
| `strength` | **서울형 "나의 재능, 강점, 기술"** ← v1에서 누락되었던 것 |
| `dream` | 서울형 "내가 원하는 삶의 모습(희망·꿈·관심사)", "시도하고 싶은 것" |
| `barrier` | 복지부 "가장 불편한 점", 서울형 "장애로 인해 겪는 사회적 제한" |
| `communication` | ELP 요소 — 어느 공식 서식에도 없으나 발달장애인 지원에는 필수 |
| `what_works` / `what_doesnt` | ELP "좋은 지원 / 피해야 할 것" — 실무자가 바뀌어도 지원의 질이 유지되게 하는 암묵지의 명시화 |

복지부형의 "가장 자주 만나는 사람은?"은 `network_entity`로 착지합니다(1차 설계에 이미 있음).

두 가지 부가 결정:
- `value_nodes.source_form_field`를 추가해 **어느 기관 서식의 어느 질문에서 나왔는지 추적**합니다
  (예: `seoul_plan.talents`). 출력 시 원래 서식으로 되돌려 보낼 때 필요합니다.
- **To/For 균형 지표는 `important_to`/`important_for` 2종만 집계**합니다.
  `strength`·`dream`은 균형 계산에 넣지 않되 '삶의 그림' 시각화에는 사용합니다.

### 4.2 계층 2 — 어휘 계층: 표준 하나를 고르지 않고, 여러 체계를 매핑

조사 결과 국내에 사례관리 욕구분류의 **단일 표준 코드체계가 사실상 부재**합니다
(개별 매뉴얼 수준). 따라서 "표준 하나 채택"이 아니라 **복수 체계 등록 + 상호 매핑**이 현실적입니다.

```
taxonomies      (code, name, source, version)      -- mohw_2024 / sis_a / gyeonggi_5 / org_custom
taxonomy_terms  (taxonomy_id, code, label, parent) -- 대분류→중분류 계층
term_mappings   (from_term, to_term, relation)     -- exact | broader | narrower | related
```

매핑 예시:

| 출발 | 관계 | 도착 |
|---|:---:|---|
| SIS-A "건강 및 안전 활동" | broader | 복지부 "신체적 건강" |
| SIS-A "건강 및 안전 활동" | related | 복지부 "정신적 건강" |
| SIS-A "사회 활동" | exact | 복지부 "문화 및 여가(사회참여)" |
| SIS-A "고용 활동" | exact | 복지부 "일자리" |

**매핑은 1:1이 아니며 손실이 발생합니다.** `relation`으로 손실 방향을 명시하고, 집계·비교 시
"exact만 쓸지, broader까지 포함할지"를 보고서마다 선택하게 합니다. 자동 변환을 믿게 하지 않는 것이 중요합니다.

기존 `support_area TEXT`는 **원문 보존용으로 그대로 두고** `support_area_term_id`를 나란히 추가합니다
(파괴적 변경 없음).

### 4.3 계층 3 — 서식 계층: 서식을 코드가 아니라 데이터로

현행 `EvalField{id, label, placeholder, rows}`를 확장해 이용계획서까지 표현할 수 있게 합니다.

```jsonc
{
  "sections": [
    { "id": "s3", "number": "3", "title": "현재 일상생활",
      "fields": [
        { "id": "life_wish", "type": "textarea", "label": "내가 내 삶에서 가장 원하는 것은?",
          "bind": { "target": "value_node", "kind": "important_to" } },
        { "id": "key_people", "type": "textarea", "label": "가장 자주 만나는 사람은?",
          "bind": { "target": "network_entity" } }
      ]},
    { "id": "s4", "number": "4", "title": "개인예산 지원영역 욕구사정",
      "fields": [
        { "id": "needs", "type": "matrix", "taxonomy": "mohw_2024",
          "columns": [{"id":"limit","label":"제한점"}, {"id":"need","label":"욕구와 희망"}],
          "bind": { "target": "value_node", "kind": "important_to", "valueColumn": "need" } }
      ]},
    { "id": "s5", "number": "5", "title": "개인예산 이용계획",
      "fields": [
        { "id": "service_plan", "type": "table", "columns": [ /* 11컬럼 */ ],
          "bind": { "target": "budget_line_item" } },
        { "id": "deduction_rate", "type": "radio", "label": "차감 이용비율",
          "options": ["변동없음","10%","15%","20%"] }
          /* bind 없음 → form_responses.extras 에 원본 보존 */
      ]}
  ]
}
```

- **필드 타입**: text / textarea / boolean / radio / checkbox / date / number / **table** / **matrix** / signature
- **`bind`**: 이 필드가 의미 계층의 무엇에 착지하는지. **bind가 없는 필드는 의미 계층에 넣지 않고**
  `form_responses.extras`에 원본 그대로 보존합니다 — 온톨로지를 행정 필드로 오염시키지 않으면서
  서식을 손실 없이 재출력하기 위함입니다.
- **렌더러는 단 하나** (`<SchemaForm>`): 입력 시 bind를 따라 의미 계층에 저장하고,
  출력 시 의미 계층에서 읽어 서식 모양으로 투영합니다.

이 설계에서 **새 기관 서식 추가 = JSON 정의 1건**입니다. 컴포넌트 개발도, DB 마이그레이션도 없습니다.
(현재는 이용계획서 기준 13개 지점 수정 + 컴포넌트 200줄)

> **왜 관리자 화면 폼 빌더가 아닌 JSON인가**: 폼 빌더 UI는 매트릭스·표·바인딩까지 지원하려면
> 개발·QA 비용이 가장 큽니다. 소규모 기관 한 곳에서 연 1~2회 발생하는 작업에 그 비용은 맞지 않습니다.
> JSON 정의는 이 저장소의 작업 방식(Claude 협업)에서 현실적으로 작성 가능하며,
> 나중에 폼 빌더를 얹더라도 **출력물이 같은 JSON**이므로 이 설계가 그대로 하부 구조가 됩니다.

## 5. 사업(Program) 개념 — 이미 현장에 존재하는 것을 데이터로

`Plan&Source/000 개별지원계획서.md`가 증거입니다.
한 당사자의 예산이 **아산사회복지재단 사업 920,000원 + 기관 자체 예산 580,000원**으로 구성되어 있고,
각각 사용 기간과 조건이 다릅니다. 즉 **한 당사자가 복수 사업에 동시 참여하는 것은 이미 현실**입니다.

`funding_sources` 테이블이 이미 다중 재원을 지원하므로, 여기에 사업을 바인딩합니다.

```
programs (code, name, operator, taxonomy_id, budget_ceiling, period_start, period_end)
funding_sources.program_id   → programs
restriction_rules.program_id → programs
form_definitions.program_id  → programs
```

효과:
- 사업마다 다른 **용처 제한이 자동 적용**됩니다 (경기 기회소득 5영역 허용 vs 복지부 주류·담배 배제).
  룰 엔진이 거래의 `funding_source_id → program_id`를 따라가 해당 사업 규칙만 평가합니다.
- 사업마다 다른 **서식과 분류체계**가 붙습니다.
- **정산·성과 보고를 사업별로 분리 산출**할 수 있습니다.

배포 모델은 **기관별 독립 인스턴스를 유지**합니다(README의 기관 담당자용 배포 가이드 = 기관마다 자기
Supabase + Vercel). 멀티테넌시는 불필요하며, 필요한 것은 "한 인스턴스 안에서 복수 사업 동시 운영"입니다.

## 6. "한 번 입력, 여러 양식 출력"의 실제 범위

이 설계의 핵심 실무 가치입니다. 다만 **100% 자동화는 불가능하며, 그렇게 약속해서도 안 됩니다.**

| 구분 | 항목 | 처리 |
|---|---|---|
| **자동 채움 가능** | 원하는 삶, 필요한 지원, 강점, 어려움, 목표, 중요한 사람, 서비스 계획, 예산 배정, 집행 실적 | 의미 계층에서 투영 |
| **자동 채움 불가** | 복지부: 활동지원 신체:가사:사회 비율, 만족도 5점, 가족사항 표, 차감 이용비율<br>서울형: 접수번호, 개인정보 동의 서명<br>공통: 작성일·작성자 등 행정 필드 | 서식별로 직접 입력 → `extras`에 보존 |

**출력 화면에 "자동 채움 N개 / 직접 확인 M개"를 명시**해, 실무자가 무엇을 검토해야 하는지 알 수 있게 합니다.
목표는 완전 자동화가 아니라 **재입력 제거**입니다 — 지금은 같은 내용을 복지부 서식, 서울 서식,
기관 ISP에 각각 쓰고 있고, 앱에 쓴 뒤 한글로 또 옮기고 있습니다.

분류체계가 다른 사업 간 이동에서도 마찬가지입니다. crosswalk가 있어도 매핑이 `broader`/`related`인 경우
사람의 확인이 필요하므로, 자동 변환된 항목은 **"확인 필요" 표시와 함께 제안**하고 실무자가 승인하게 합니다.

## 7. 통합 로드맵 (1차 보고서 Phase 0~4와 재조정)

| 순서 | 내용 | 1차 로드맵과의 관계 | 기간 |
|:---:|---|---|:---:|
| **0** | 성능 교정 (리전 정렬·요청 내 캐싱·병렬화) | 1차 Phase 0 그대로 — **최우선 유지** | 1주 |

| **1** | 서비스자원 + 룰엔진 **+ programs 바인딩** | 1차 Phase 1에 사업 개념 결합 (규칙이 사업별이므로) | 2~3주 |
| **B** | **어휘 계층** — taxonomies·terms·mappings, 복지부8·SIS-A8·경기5 시드 | **신규**. 1차 Phase 2와 결합 (value_nodes 만들 때 term_id 함께) | +1주 |
| **2** | 가치노드(**8종 kind**) + 파생 엣지 + To/For 균형 | 1차 Phase 2 (kind 확장 반영) | 2~3주 |
| **C** | **서식 계층 — 출력 먼저**: form_definitions + 출력 렌더러 + 인쇄 CSS, 기존 2서식을 JSON으로 이관 | **신규** | 2~3주 |
| **3** | 7단계 워크플로 (budget_cycles) | 1차 Phase 3 | 1~2주 |
| **D** | **서식 계층 — 입력**: SchemaForm 입력 렌더러, 이용계획서 하드코딩 13개 지점 제거 | **신규** | 2~3주 |
| **4** | 관계망 + SNA + 보안 | 1차 Phase 4 | 3~4주 |

**총 기간: 1차 9~13주 → 13~19주.**

**출력(C)을 입력(D)보다 먼저 두는 이유** 세 가지:
1. 이용계획서 인쇄 경로가 **아예 없어** 실무자가 한글로 재작성 중입니다 — 출력만으로 즉시 실무 가치가 발생합니다.
2. 출력 렌더러가 **서식 스키마의 검증대** 역할을 합니다. 스키마가 부족하면 출력에서 먼저 드러납니다.
3. 입력 화면 교체는 실무자 재학습을 요구하므로 뒤로 미룹니다.

**A(P0 버그)를 맨 앞에 두는 이유**: 지금은 평가 서식을 PCP에서 바꾸는 순간 당사자가 빈 편지를 받고,
서식을 오가면 기존 데이터가 사라집니다. 이 상태에서 서식을 늘리는 것은 결함을 증폭시키는 일입니다.
