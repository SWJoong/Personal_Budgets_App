# 온톨로지 기반 사례관리 개편 검토 보고서 (v1)

> **작성일**: 2026-07-23
> **대상**: 아름드리꿈터 자기주도 개인예산 관리 앱 (Next.js 16 + Supabase, Vercel 배포 운영 중)
> **기준 문서**: 「장애인복지 분야 비영리기관의 PCP 및 개인예산제 지원을 위한 온톨로지 기반 사례관리 데이터베이스 설계 방안과 시스템 고도화 모델」(첨부 리서치)
> **부록 산출물**: `ontology/pcp_ontology.dtdl.json` (Ontology Playground 업로드용), `ontology/ontology_schema_draft.sql` (스키마 초안)

## 1. 요약 (Executive Summary)

**결론: 새 앱을 만들지 않고, 지금의 앱을 5단계에 걸쳐 점진 개편할 것을 권고합니다.**

핵심 근거 세 가지:

1. **기존 DB에 온톨로지의 골격이 이미 있습니다.** 리서치가 요구하는 8개 클래스 중 4개(Person·Supporter·Budget_Plan·Transaction)와, "욕구 → 계획 → 예산 → 집행"을 잇는 논리적 연쇄망(Ontological Chain)이 `care_plans → support_goals(To/For 구분 포함) → monthly_plans → transactions` FK 사슬로 이미 구현되어 있습니다. 목표 모델은 현재 스키마의 **확장**이지 부정이 아닙니다. 추정 코드 재사용률은 약 85%입니다.

2. **실사용에서 겪은 "전 화면 공통 반응속도 저하"는 재작성 사유가 아닙니다.** 원인은 아키텍처가 아니라 ① 서버 함수 리전 미지정(`vercel.json` 부재 — 기본 미국 동부에서 실행될 개연성) × 서울 Supabase 간 물리 거리, ② 화면당 직렬 DB 왕복 11~13회의 누적입니다(왕복당 약 190ms × 11~13회 ≈ 2.1~2.5초). 어떤 프레임워크로 다시 만들어도 같은 패턴이면 같은 속도가 나오고, 반대로 리전 정렬과 병렬화만으로 현재 코드가 0.3초 내외로 내려갑니다. **성능은 "다시 만들 이유"가 아니라 "Phase 0에서 먼저 고칠 항목"입니다.**

3. **소규모 기관 운영 현실에 신규 스택은 위험만 더합니다.** 수십 명 규모의 지식그래프는 Postgres 뷰와 재귀 쿼리로 충분하며, 관리형 Supabase에서 그래프 확장(Apache AGE)이 지원되지 않는 제약도 "정형 테이블 + 파생 엣지 뷰" 하이브리드 설계로 우회됩니다. 외부 그래프 DB(Neo4j 등) 병행은 무료 티어가 있어도 제2 저장소의 백업·동기화·장애 대응이라는 상시 운영 부담을 만듭니다.

개편 로드맵(총 9~13주): **Phase 0 성능 교정(1주) → Phase 1 서비스자원+룰엔진(2~3주) → Phase 2 가치노드+그래프(2~3주) → Phase 3 7단계 워크플로(1~2주) → Phase 4 관계망+SNA+보안(3~4주)**. 각 단계는 무중단·추가형(additive)이며 단계별 롤백이 가능합니다.

## 2. 현행 시스템 진단

### 2.1 현재 데이터 구조 (테이블 16개)

```
profiles (역할: admin/supporter/participant, is_super_admin)
 └─ participants (예산 기본값, 배정 실무자, ui_preferences)
     ├─ funding_sources (재원별 예산·잔액 — 트리거 자동 재계산)
     ├─ transactions (지출: 금액·카테고리·영수증·활동사진·위치·pending/confirmed)
     │    └─ monthly_plan_id ─→ monthly_plans
     ├─ plans (오늘 계획: 선택지 비교)
     ├─ monthly_plans (월별 계획 1~6개, planned_budget, easy_description)
     │    └─ support_goal_id ─→ support_goals
     ├─ care_plans (이용계획서/개별지원계획서, JSONB)
     │    ├─ support_goals (연간 지원목표: is_to_goal/is_for_whom, 지원영역, easy_description)
     │    └─ budget_line_items (예산 세목: 관·항·목, 금액 자동계산, support_goal_id)
     ├─ evaluations (월별 4+1 평가) ─ goal_evaluations (목표별 4+1)
     ├─ sis_assessments (SIS-A 지원필요도 사정)
     ├─ file_links / participant_feedback
     └─ (인증) user_invitations — Google OAuth 사전등록 전환 중
system_settings (키-값 설정)
```

### 2.2 이미 구현되어 있는 PCP 요소 — 생각보다 많습니다

| PCP/개인예산제 개념 | 현재 구현 | 위치 |
|---|---|---|
| Important To / Important For 구분 | ◯ (불리언 2개) | `support_goals.is_to_goal`, `is_for_whom` (마이그레이션 24) |
| SIS-A 기반 지원영역 8분류 | ◯ (자유 텍스트) | `support_goals.support_area` + `sis_assessments` |
| 4+1 평가 (시도한 것/배운 것/만족/불만족/향후계획) | ◯ | `evaluations` + `goal_evaluations` |
| 욕구→계획→예산→집행 연쇄 | ◯ (FK 사슬) | care_plans → support_goals → monthly_plans → transactions |
| 예산 관·항·목·세목 | ◯ | `budget_line_items` (금액 GENERATED 컬럼) |
| 쉬운 정보(Easy Read) 병기 | ◯ | `easy_description`/`easy_image_url` (마이그레이션 30) + TTS |
| 집행 검토 워크플로 | △ (수동 2단계) | `transactions.status` pending→confirmed + 검토 대기열 화면 |

개별지원계획서 양식(`Plan&Source/000 개별지원계획서.md`)에도 "나에게 중요한 것/나를 위해 중요한 것" 표가 이미 자리 잡고 있어, **도메인 개념 차원에서 이 앱은 이미 사람중심계획을 지향**하고 있습니다. 문제는 이 개념들이 "관계(엣지)"가 아니라 평면 텍스트·불리언·JSONB로 저장되어 리서치가 지적하는 "기계가 해석할 수 있는 관계 중심 구조"에 못 미친다는 점입니다.

### 2.3 성능 진단 — 전 화면 공통 저하의 원인 분해

실사용 피드백("반응속도가 매우 느려 실사용이 어려움", 전 화면 공통)과 코드 분석이 일치하는 원인 3가지:

| # | 원인 | 근거 | 영향 |
|---|---|---|---|
| 1 | **서버 함수 리전 미지정** | 저장소에 `vercel.json` 없음 → Vercel 서버리스 함수가 기본 리전(iad1, 미국 동부)에서 실행될 개연성. Supabase는 서울(README 권장 설정) | DB 왕복당 약 180~200ms (서울↔미 동부). 같은 리전이면 2~5ms |
| 2 | **화면당 직렬 DB 왕복 11~13회** | 예: 당사자 홈 = proxy(인증+프로필) → 페이지(인증+프로필+예산) → 거래 3종 → signed URL 생성(내부 인증 재호출+버킷별 순차) → 월별계획(2쿼리 순차) → 계획 이미지 건별 signed URL → 평가 | 190ms × 11~13회 ≈ **2.1~2.5초/페이지**. 모든 화면이 같은 패턴이므로 "전 화면 공통" 체감과 정확히 부합 |
| 3 | **요청 내 중복 조회·미캐싱** | `React cache()`/`unstable_cache` 사용 0건, 레이아웃·페이지·서버 액션이 같은 요청에서 인증·프로필을 각각 재조회, Suspense 스트리밍 미사용 | 1·2번을 증폭 |

**중요한 함의**: 세 원인 모두 프레임워크·DB 선택과 무관한 **설정과 코드 패턴 문제**입니다. 신규 앱으로 재작성해도 같은 패턴을 쓰면 같은 속도가 나옵니다. 교정 방법은 §6 QA·§10 Phase 0에 정리했습니다.

> 확인 필요(저장소 밖 정보): Vercel 대시보드에서 함수 리전이 별도 설정되어 있는지, Supabase 프로젝트 리전이 실제 ap-northeast-2(서울)인지 — §9 추가 필요 자료 참조.

### 2.4 개편 전 정리가 필요한 잠복 결함 4건

개편 여부와 무관하게 존재하는 결함으로, 온톨로지 레이어를 얹기 **전에** 정리해야 안전합니다.

1. **잔액 이중 관리**: DB 트리거(전액 재계산)와 서버 액션의 수동 잔액 보정이 공존 — 같은 수정에서 이중 반영될 수 있는 구조. 트리거 단일 정본화 필요.
2. **RLS 신·구 이원화**: 초기 정책(`auth_user_id` 매핑)과 후기 정책(`participant_id = auth.uid()` 직접 비교)이 혼재. Google OAuth 전환으로 두 값이 달라지는 계정이 생기면 열람 구멍 또는 차단이 발생.
3. **타입 파일 구식화**: `src/types/database.ts`가 마이그레이션 21~31(월별계획·지원목표·평가·세목 등)을 미반영 — `npm run generate-types` 재실행 필요.
4. **care_plans JSONB 이중 구조**: 지원목표가 정규 테이블로 이관(마이그레이션 28)된 후에도 JSONB 원문이 병존 — 문서 스냅샷으로 격하하고 편집 경로를 정규 테이블로 단일화해야 그래프 파생이 이중화되지 않음.

## 3. 온톨로지 모델 요구사항 정리 (리서치 보고서 기준)

**클래스 8개**: Person(당사자) · Supporter(지원자) · Value_Node(Important_To/Important_For 하위클래스) · Network_Entity(가족·이웃 등 비공식 관계망) · Service_Resource(서비스 제공기관·용처) · Budget_Plan(ISP/개인예산계획) · Transaction(집행) · Restriction_Rule(오남용 제한 규칙)

**엣지 9개**: has_Important_To · requires_Important_For · facilitates_plan_for · is_addressed_by · allocates_funds_to · makes_transaction · is_spent_at · violates_rule(조건부) · reports_status_of

**기능 요구 7개**:
① To/For 균형 추적(엣지 수·가중치 비교 → 불균형 알림)
② 룰 엔진(집행 발생 시 자원 속성·제한 규칙 검사 → 오남용 의심 플래그)
③ 개인예산제 7단계 프로세스(신청→욕구상담→계획작성→심의승인→지급→집행모니터링→정산평가) 상태 관리
④ 지식그래프 기반 SNA(고립 위험 예측)·맞춤 자원 추천
⑤ 외부 AI 전송 시 비식별화
⑥ 역할별 서브그래프 접근 제어
⑦ 개방형 표준 API 상호운용성(행복e음 등 연동 대비)

## 4. 격차 분석 (Gap Analysis)

### 4.1 클래스 매핑

| 온톨로지 클래스 | 상태 | 현재 대응 | 개편 방안 |
|---|:---:|---|---|
| Person | ◯ | `participants` + `profiles` | 유지 |
| Supporter | ◯ | `profiles(role)` + `assigned_supporter_id` | 유지 (다중 담당 필요 시 `participant_supporters` 추가) |
| Budget_Plan | ◯ | `care_plans` + `budget_line_items` + `monthly_plans` | 유지 + 사이클 상태는 신규 `budget_cycles` |
| Transaction | ◯ | `transactions` | 유지 + `service_resource_id` FK 추가 |
| Value_Node (To/For) | △ | `support_goals.is_to_goal/is_for_whom` **불리언** — 독립 엔티티·가중치·이력 없음 | 신규 `value_nodes` 로 승격 (백필 규칙 §5.3) |
| Service_Resource | ✕ | `place_name` **자유 텍스트** + `linked_services` TEXT | 신규 `service_resources` (기존 위치 데이터 백필) |
| Restriction_Rule | ✕ | 없음 (사람이 pending→confirmed 수동 검토) | 신규 `restriction_rules` + `rule_violations` + 룰 엔진 |
| Network_Entity | ✕ | 없음 | 신규 `network_entities` |

### 4.2 엣지 매핑

| 엣지 | 상태 | 현재 대응 → 개편 방안 |
|---|:---:|---|
| makes_transaction | ◯ | `transactions.participant_id` FK — 파생 뷰로 노출 |
| facilitates_plan_for | ◯ | `participants.assigned_supporter_id` FK — 파생 뷰로 노출 |
| is_addressed_by | △ | 목표→계획 FK는 있으나 "가치→계획"이 아님 → `support_goals.value_node_id` 추가로 완성 |
| allocates_funds_to | △ | 세목→목표 FK는 있으나 "→용처"가 없음 → `budget_line_items.service_resource_id` 추가 |
| has_Important_To / requires_Important_For | △ | 불리언 → `value_nodes` 승격 후 파생 |
| is_spent_at | ✕ | `place_name` 텍스트 → `transactions.service_resource_id` FK |
| violates_rule | ✕ | 없음 → `rule_violations` 테이블 |
| reports_status_of | ✕ | 없음 → `network_entities` + 물리 엣지(접촉 기록) |

### 4.3 기능 매핑

| 기능 요구 | 상태 | 격차 요지 |
|---|:---:|---|
| ① To/For 균형 추적 | ✕ | 데이터는 있으나(불리언) 지표·알림 없음 → §5.3 |
| ② 룰 엔진 | ✕ | 전적으로 수동 검토 → §5.4 |
| ③ 7단계 워크플로 | ✕ | 단계 개념 자체가 없음 → §5.5 |
| ④ SNA·자원 추천 | ✕ | 관계망 데이터 부재가 선행 격차 → Phase 4 |
| ⑤ AI 비식별화 | △ | 현재 AI 호출(OCR·쉬운요약)에 성명은 미포함이나 공식 게이트웨이 없음 → `deidentify.ts` 공통 유틸 |
| ⑥ 서브그래프 접근 제어 | △ | 역할 단위 RLS는 있으나 **모든 실무자가 모든 당사자 열람** — 담당자 단위 제어 없음 → RLS 헬퍼 `is_assigned()` |
| ⑦ 개방형 API | △ | Supabase 자동 REST/GraphQL(pg_graphql)이 잠재 자산 — 표준 스키마 공개는 후속 과제 |

**격차 분석 결론**: 8클래스 중 4◯·1△·3✕, 9엣지 중 2◯·3△·4✕. 없는 것은 "새 테이블 6~7개와 뷰 2개"로 만들 수 있고, 있는 것은 그대로 쓸 수 있습니다. **전면 재설계가 아니라 증축입니다.**

## 5. 개편 설계안

### 5.1 타깃 아키텍처: 세 가지 선택지 비교

| 기준 | **A. 정형 테이블 + 파생 엣지 오버레이 (권고)** | B. 완전 트리플 스토어 (Postgres 안 EAV/RDF) | C. 외부 그래프 DB 병행 (Neo4j AuraDB Free) |
|---|---|---|---|
| 기존 서버 액션 21개·컴포넌트 81개 | 그대로 유지 (추가형) | 전면 재작성 (모든 쿼리가 주어-술어-목적어 조인) | 유지되나 동기화 코드 신규 |
| RLS·권한 | 기존 정책 위에 신규 테이블 정책만 추가 | 트리플 단위 RLS는 표현력 부족·성능 저하 | Neo4j에 RLS 없음 → 앱 레이어 재구현 |
| 잔액 트리거·GENERATED 컬럼 등 DB 자산 | 유지 | 폐기 | 유지 (단 이중 저장) |
| 그래프 탐색 성능 (수십 명 규모) | 재귀 CTE로 충분 (노드 수천 개 미만) | 조인 폭발로 가장 불리 | 최고이나 과잉 성능 |
| 운영 (비개발자, SQL Editor 수동 관례) | 관례 유지 | 디버깅 난도 급상승 | 제2 저장소 백업·동기화·장애 대응 부담. Free 티어는 장기 미접속 시 일시정지 정책 리스크 |
| 추가 비용 | $0 | $0 | $0이지만 운영 인건비 증가 |
| Apache AGE 미지원 제약 | 무관 | 무관 | 회피 가능하나 불필요 |

**권고: 옵션 A.** 원칙은 두 가지입니다.

- **정형 우선**: 온톨로지 클래스마다 정형 테이블을 둡니다(§4.1의 신규 테이블). 화면·RLS·트리거 등 기존 자산이 그대로 동작합니다.
- **파생 우선(derived-first) 그래프**: 그래프 "읽기"는 `v_graph_edges` 뷰 하나로 통합합니다. FK로 표현되는 관계는 뷰에서 **파생**하고(저장하지 않음), FK로 표현 불가능한 관계(관계망 접촉 기록, AI 추천 관계)만 `graph_edges` 테이블에 물리 저장합니다. 같은 사실을 두 곳에 기록하는 이중 기록은 금지 — 이 코드베이스에 이미 있는 "잔액 트리거 + 수동 보정 충돌"(§2.4)과 같은 드리프트를 재생산하지 않기 위함입니다.

테이블·뷰의 컬럼 수준 설계는 **부록 B(`ontology/ontology_schema_draft.sql`)** 에 전문이 있습니다. 시각 검증용 온톨로지 정의는 **부록 A(`ontology/pcp_ontology.dtdl.json`)** 를 Microsoft Ontology Playground에 업로드하면 노드-엣지 다이어그램으로 확인할 수 있습니다.

### 5.2 SNA·추천 연산의 분리

고립 위험·자원 추천 같은 그래프 연산은 화면 응답 경로에서 분리합니다. `v_graph_edges`를 소스로 하는 materialized view(`mv_graph_metrics`)를 만들고 Supabase가 지원하는 `pg_cron`으로 야간 갱신 — 무거운 연산이 사용자 응답 속도에 개입하지 않습니다(성능 문제 재발 방지 원칙).

### 5.3 To/For 균형 추적

- **데이터 승격**: `support_goals`의 불리언을 독립 `value_nodes`(kind=important_to|important_for, weight 0~5, 이력 상태)로 승격. 백필 규칙: To만 체크→To 노드 1행, For만→For 1행, 둘 다→2행(라벨 동일), 미체크→미생성(실무자 후속 입력). 한 Phase 동안 불리언을 읽기 전용으로 병행해 기존 화면 무중단.
- **2층위 지표**: "가치 선언 층위"(To/For 노드 수·가중치)와 "예산 배분 층위"(가치→목표→세목 배정액 합)를 함께 계산하는 `v_to_for_balance` 뷰. 선언은 균형이어도 돈이 전부 For로 갈 수 있기 때문에 두 층위가 모두 필요합니다. 균형지수 = (To가중치−For가중치)/총가중치, −1(전부 For)~+1(전부 To).
- **알림 판정**: 노드 4개 이상이고 |균형지수| > 0.4 → 불균형 알림("당사자 스스로의 목표 설정이 부족합니다" 등), 계획에 연결되지 않은 가치 존재 → 미반영 알림. 별도 알림 테이블 없이 조회 시 계산(수십 명 규모에 충분).
- **알림 노출 지점**: ① 실무자 당사자 목록 배지 ② 계획 편집기 저장 시 인라인(심의 제출 전 자연 교정) ③ 월별 평가 화면 옆 추이 ④ 당사자 홈 선택 블록 "내 마음 저울"(§6 easy-read).

### 5.4 룰 엔진 (스마트 컨트랙트 개념의 현실적 구현)

- **검사 지점**: 판정 로직을 SQL 함수 `f_check_transaction_rules()` **하나**로 작성하고, (a) `transactions` 트리거가 호출해 `rule_violations`에 기록(정본 — 수동 입력·OCR·CSV 가져오기 등 모든 유입 경로 커버, 추가 왕복 0회), (b) 거래 등록 폼은 같은 함수를 RPC로 호출해 저장 전 사전 경고(UX 보조). 단일 소스 유지.
- **규칙 표현**: 6종 rule_type(키워드 차단/카테고리 차단/단건 한도/월별 카테고리 한도/자원 위험태그/빈도 한도) × JSONB 파라미터. 기관 공통(global)과 개인별(participant) 범위 지원.
- **기존 흐름과의 결합**: `pending/confirmed` 2상태를 그대로 두고 위반은 별도 테이블로 표현 — 기존 화면·잔액 트리거 무변경. `severity='block'`인 미해소 위반이 있으면 confirmed 전환을 트리거가 거부하되, 실무자가 사유를 기록하고 기각(dismissed)하면 승인 가능.
- **원칙 — 자동 거절 없음**: 리서치의 "실시간 차단"을 그대로 구현하면 당사자의 자기결정권과 충돌합니다. 시스템은 **플래그와 근거**만 만들고 최종 판단은 사람이 합니다(기각 사유는 감사 추적으로 남음). 이는 리서치 5.4의 "오남용 의심 플래그 전송" 취지와도 부합합니다.

### 5.5 개인예산제 7단계 워크플로

- 문서 테이블(`care_plans`)이 아닌 **신규 `budget_cycles`**(당사자×연도 1행)에 stage를 둡니다. 이유: 신청·욕구상담은 계획서 생성 이전, 지급·집행·정산은 이후의 사건이므로 문서에 상태를 붙이면 단계가 문서 존재에 종속되고, 한 연도에 복수 양식(보건복지부형/서울형)이 공존할 수 있기 때문입니다.
- 모든 전이는 `budget_cycle_events`에 기록(누가·언제·왜) — 심의 의견·반려 사유가 그대로 감사 추적이 됩니다. 전이는 순방향 1단계 + 반려 역행 2종만 허용.
- **소프트 게이팅으로 시작**: 운영 중 데이터가 어느 단계에도 완벽히 맞지 않는 현실을 흡수하기 위해, 초기에는 단계 미달 시 경고 배너만 표시하고 차단하지 않습니다. 차기 연도 사이클부터 "승인 전 지급 불가" 하드 게이트를 시스템 설정으로 선택 제공.

## 6. 역할별 검토 (제시된 역할별 프롬프트에 대한 답)

### 6.1 /backend — "기존 로직과 온톨로지형 DB가 충돌하지 않는가? 새로 구축한다면 어떤 플랫폼인가?"

**충돌 여부: 구조적 충돌은 없으나, 선결 정리 2건과 설계 원칙 준수가 조건입니다.**

1. **잔액 트리거 충돌 (선결)**: 현행 잔액 자동 재계산 트리거와 서버 액션의 수동 잔액 보정이 공존합니다. 여기에 룰 엔진 트리거를 얹기 전에 트리거를 단일 정본으로 정리(수동 보정 코드 제거)해야 하며, 트리거 이름에 실행 순서 접두(`trg_10_balance`, `trg_20_rules`)를 부여해 순서를 명시해야 합니다.
2. **RLS 이원화 정리 (선결)**: 신·구 정책이 혼재한 상태에서 담당자 단위 서브그래프 제어를 얹으면 검증이 불가능해집니다. `is_self()`/`is_staff()`/`is_assigned()` 헬퍼 3종으로 통일 후 신규 테이블에 일관 적용해야 합니다.
3. **JSONB 이중구조**: 파생 엣지의 소스는 정규 테이블로 한정하고 `care_plans.content` JSONB는 제출 문서 스냅샷으로 격하 — 같은 관계가 두 소스에서 이중 파생되는 사고를 방지합니다.
4. **폴리모픽 엣지 무결성**: `graph_edges`는 FK를 걸 수 없으므로 endpoint 존재 검증 트리거와, 엔티티 삭제 시 관련 엣지를 `valid_to`로 마감(삭제 대신 종료 — 관계 소멸 이력이 SNA의 입력이 됨)하는 트리거가 필요합니다.
5. **데모 모드 주의**: 데모 모드는 service-role 클라이언트로 RLS를 전면 우회하므로, 접근 제어 검증은 반드시 실모드에서 수행해야 합니다.

**플랫폼 평가: "새 관계형 DB 구축" 불필요 — 현행 Supabase(Postgres) 유지가 최적입니다.**

- 관리형 Supabase는 그래프 확장 Apache AGE를 지원하지 않으나(§9 조사 출처), 수십 명 규모에서는 정형 테이블 + `v_graph_edges` 파생 뷰 + 재귀 CTE로 그래프 질의가 충분히 처리됩니다.
- `pg_graphql`(Supabase 내장)은 그래프 DB가 아니라 관계형 스키마의 GraphQL API 노출 도구입니다 — 다만 §3-⑦ 상호운용성 요구에는 유용한 자산입니다.
- Neo4j AuraDB Free는 실재하나($0, 약 20만 노드 규모) 제2 저장소 동기화·백업·계정 관리 부담이 소규모 기관에 비적합. **수만 노드 이상 상시 그래프 알고리즘이 필요해지는 시점에만 재검토**하십시오.

### 6.2 /devops — "현재 인프라에서 온톨로지 기반 앱으로 갈 때의 문제와 장점은?"

**문제(리스크)**:
1. 리전 정렬을 먼저 하지 않으면 온톨로지 조회(조인 증가)가 지연을 **증폭**시킵니다 — Phase 0이 반드시 선행되어야 하는 이유.
2. 마이그레이션 수동 실행 관례(SQL Editor)에서 신규 파일 8~9개가 추가되므로, 파일마다 전/후 검증 쿼리를 내장하고 "DB 선실행 → 앱 배포" 순서를 PR 체크리스트로 문서화해야 합니다.
3. 데모 모드/실모드 이원 운영 중 인증 전환(Google OAuth)이 진행되고 있어, 접근 제어 강화(Phase 4)는 인증 전환 완료 이후로 배치해야 검증이 유효합니다.

**장점**:
1. **인프라 변경이 사실상 `vercel.json`(리전 서울 고정) 한 파일**입니다. 신규 서비스·환경변수 0개, 추가 비용 $0.
2. 그래프 배치 연산은 Supabase 지원 `pg_cron`으로 처리 — 외부 스케줄러·Edge Function 불필요.
3. 이미 도입된 Vercel Speed Insights로 개선 전/후 성능을 정량 비교할 수 있습니다(p75 TTFB/LCP).
4. 비식별화 게이트웨이는 코드 레벨 유틸(`deidentify.ts` — OpenAI 호출 전 이름·기관명 토큰 치환)로 충분 — 네트워크 구성 변경 없음.

### 6.3 /easy-read-review — "PCD·삶의 그림을 당사자 중심 정보로 앱에서 어떻게 보여줄까?"

사람중심 실천 현장에서 쓰이는 도구 — 사람중심설명(PCD), 한 장 소개서(OPD, One Page Description), 삶의 그림(POL, Picture of a Life), 꿈 찾기(PATH) — 를 조사한 결과(§9 출처), 온톨로지의 1-hop 그래프가 곧 "삶의 그림"의 데이터 형태임을 확인했습니다. 제안:

1. **"나의 그림" 화면**: 당사자를 중앙에 둔 방사형 1-hop 그림. 4개 구역 — "내가 좋아하는 것(To)" / "나에게 필요한 것(For)" / "나의 사람들(관계망)" / "내가 가는 곳(자원)". 한 화면 노드 **7±2개 제한**(인지 부하), 각 노드는 사진(`easy_image_url`) + 짧은 라벨, 탭하면 기존 TTS가 읽어줌.
2. **To/For 균형은 숫자 없이**: 균형지수 대신 **시소(저울) 그림** 메타포 — "내가 하고 싶은 것"과 "나에게 필요한 것"이 양쪽에 앉아 있는 그림. 색+모양 이중 부호화, 7색 테마의 WCAG AA 대비 유지.
3. **비낙인 문구 원칙**: 룰 위반의 당사자 노출 문구는 규칙마다 `easy_message`로 저장하며 기본형은 "이 지출은 선생님과 같이 확인해요" — 금지·위반·오남용 같은 어휘를 당사자 화면에서 배제합니다.
4. **7단계의 당사자 표시는 3단계로 축약**: "계획 만들어요 → 돈을 써요 → 같이 돌아봐요". 행정 단계명(심의·정산 등)은 실무자 화면에만.
5. 모든 신규 엔티티(value_nodes·service_resources·network_entities)에 `easy_description`/`easy_image_url`을 **처음부터** 포함(마이그레이션 30 관례 계승) — 쉬운 정보가 나중에 덧붙는 구조를 만들지 않습니다.

### 6.4 /frontend — "실무자용 UI/UX 변화와 당사자 개인화 대응은?"

**실무자 화면**:
1. **그래프 편집은 폼, 그래프는 읽기 전용 시각화**: 노드-링크 캔버스를 직접 편집시키는 UI는 오조작·학습 비용 대비 이득이 없습니다. 기존 계획 편집기에 "가치 선택"·"자원 선택" 필드를 추가하는 폼 기반 입력을 유지하고, 그래프 뷰는 조회 전용으로 제공합니다.
2. 시각화는 수십 노드 규모이므로 d3-force 또는 자체 SVG 방사형 배치로 충분 — React Flow급 편집 라이브러리는 번들 비용 과잉.
3. **신규 정보구조 최소화**: 균형 배지·위반 배지·7단계 스텝퍼를 기존 화면(당사자 목록·상세·영수증 검토 대기열)에 삽입합니다. 신규 최상위 메뉴는 "자원 관리" 1개만.
4. 위반 처리 흐름은 기존 검토 대기열 안에서 완결(위반 상세 → 사유 입력 → 기각/확정 모달) — 실무자가 새 동선을 배우지 않게 합니다.

**당사자 개인화**: 기존 `ui_preferences.enabled_blocks`(홈 구성 요소 켜고 끄기) 패턴을 재사용해 "내 마음 저울", "나의 사람들", "나의 그림" 블록을 **opt-in**으로 추가합니다. 당사자가 제안하는 UI 변경은 이 블록 단위 선택 + 기존 7색 테마·꾸미기 체계로 흡수하고, 블록화 구조 덕분에 이후 새로운 개인화 요구도 블록 추가로 대응할 수 있습니다.

### 6.5 /pl — "온톨로지형 앱에서 중요하게 봐야 하는 지점과 기술 스택은?"

**중요 지점 5가지**:
1. **파생 우선 원칙**: 같은 사실을 두 곳에 저장하지 않는다(FK가 정본, 그래프는 뷰). 이 원칙이 무너지면 잔액 이중 관리와 같은 정합성 사고가 그래프 전체로 확산됩니다.
2. **성능 선행**: Phase 0 없이 온톨로지 조인을 얹으면 "느린 앱"이 "더 느린 앱"이 됩니다.
3. **데이터 입력 부담의 상한**: 실무자 신규 입력은 "자원 확인·병합"과 "관계망 등록" 두 가지로 한정하고, 나머지(가치 백필·자원 자동 매칭·엣지 파생)는 시스템이 만든다 — 리서치 7.2의 소진 예방 요구.
4. **자동 결정 금지**: 룰 엔진·AI 추천은 플래그와 제안까지만. 사람의 결정을 대체하는 지점이 생기지 않도록 코드 리뷰 기준에 명시.
5. **인증 전환과의 순서**: 서브그래프 접근 제어는 Google OAuth 전환 완료 후에만 유효 — 로드맵상 Phase 4에 배치.

**기술 스택 권고**: 현행 유지 + 최소 추가.
- 유지: Next.js 16(App Router) / React 19 / Supabase(Postgres·Auth·Storage) / Tailwind 4 / Vercel / GPT-4o / 카카오맵
- 추가: `vercel.json`(리전), React `cache()`(요청 내 캐싱), d3-force 또는 자체 SVG(그래프 뷰), pg_cron(배치), DTDL v3 + Microsoft Ontology Playground(스키마 협업 검증 — 부록 A)
- 도입하지 않음: 외부 그래프 DB, 별도 백엔드 서버, 상태관리 라이브러리 추가

### 6.7 /qa — "적용 전후의 기술적 불안정과, 느린 반응속도를 반영한 개편 포인트는?"

**적용 전(현재) 불안정**: 잔액 이중 관리(§2.4-1), RLS 이원화(§2.4-2), 타입 파일 구식화 — 온톨로지와 무관하게 지금도 존재하는 리스크이며 Phase 0~1에서 해소.

**적용 후(개편 중) 불안정과 대비책**:
1. **백필 정합성**: Phase별 마이그레이션에 전/후 카운트 검증 쿼리 내장(마이그레이션 28의 관례 재사용) — 예: value_nodes 행 수 = To/For 체크 합, place_name→자원 매칭 누락 0건.
2. **트리거 상호작용**: 거래 INSERT/UPDATE/DELETE × {잔액 재계산, 룰 검사, confirm 차단} 회귀 매트릭스. 특히 "block 위반 존재 시 confirm 거부 + 잔액 불변" 시나리오.
3. **RLS 회귀**: 역할 3종 × 담당/비담당 × 신규 테이블 5종 접근표. Phase 4에서 담당자 제한 도입 시 "전체 조회 전제"로 만들어진 기존 실무자 화면이 빈 화면이 되는 회귀가 최대 위험.
4. **이중 경로 테스트**: 데모/실모드, 수동 입력/OCR/CSV 세 유입 경로의 룰 플래그 동작을 vitest 통합 테스트로 고정.

**반응속도 반영(재발 방지 설계)**:
- **기준선**: 착수 전 주요 5화면(홈·달력·거래장부·계획·평가)의 TTFB/LCP p75를 Speed Insights로 기록. **목표: 홈 TTFB 300ms 이하.**
- **Phase 0 교정 항목**: ① `vercel.json` 리전 서울 고정 ② React `cache()`로 요청 내 인증·프로필 중복 조회 제거 ③ 미들웨어(proxy)의 DB 왕복을 JWT 클레임 검증으로 대체 ④ 직렬 쿼리 병렬화(Promise.all) ⑤ signed URL 배치 생성(건별 루프 제거) ⑥ Suspense 스트리밍으로 첫 화면 체감 개선 ⑦ 검토 대기열·잔액 집계용 부분 인덱스 ⑧ RLS의 EXISTS 서브쿼리를 STABLE 헬퍼 함수로 교체(행당 재평가 제거).
- **온톨로지 단계의 성능 게이트**: 매 Phase 종료 시 기준선 재측정, 회귀 발견 시 다음 Phase 진입 불가. 그래프 연산은 materialized view + 야간 배치로 화면 경로에서 격리(§5.2).

### 6.8 /ux-ui — "당사자 중심으로 개편해온 기존 UI/UX에서, 실무자도 편리한 환경은?"

1. **실무자의 반복 업무를 그래프가 대신 채우게**: 영수증 정산 시 자원 자동 매칭(카카오 장소 ID 기반), 위반 자동 플래그, 계획-거래 자동 연결 제안 — 실무자는 확인·수정만. "입력할 것이 늘어나는 시스템"이 아니라 "대조 작업이 줄어드는 시스템"으로 체감되게 하는 것이 수용성의 관건입니다.
2. **한 화면 완결 동선**: 검토 대기열에서 승인 판단에 필요한 정보(영수증 이미지·연결 계획·위반 여부·잔액 영향)를 한 화면에 모아 화면 전환 없이 승인/반려까지.
3. **당사자별 "사례 요약 헤더"**: 실무자 상세 화면 상단에 7단계 스텝퍼 + To/For 저울 + 관계망 미니 그림을 상시 노출 — 사례회의 때 이 화면 하나로 브리핑 가능.
4. **일괄 작업**: 월말 정산·평가 시즌의 반복 작업(여러 당사자 평가 발행, 규칙 일괄 적용)을 목록 화면에서 다건 선택으로.
5. **키보드·데이터그리드 관성 유지**: 거래장부는 회계장부형 그리드 UX를 유지하고, 온톨로지 요소(자원·계획 연결)는 그리드의 셀 선택기로 통합 — 별도 화면으로 분리하지 않습니다.

## 8. 신규 제작 vs 기존 개편 — 당초 목적과의 비교 검토

### 8.1 당초 목적과의 정합

이 앱의 당초 목적(기획서 v5)은 "당사자의 자기주도성 강화 — 스스로 계획하고 확인하는 주체"였고, 온톨로지 리서치의 목적은 "당사자를 관계의 중심에 두는 데이터 구조"입니다. **두 목적은 동일한 철학의 다른 층위**(UI 층위 ↔ 데이터 층위)이며, 온톨로지 도입은 당초 목적의 폐기가 아니라 데이터 층위로의 심화입니다. 신규 앱을 만들 경우 오히려 당초 목적을 위해 쌓은 자산(잔액 시각화, 쉬운 정보 체계, 선택지 비교)을 재구현하며 목적 달성이 후퇴하는 기간이 생깁니다.

### 8.2 판단 매트릭스

| 기준 | 판정 | 근거 |
|---|:---:|---|
| 당초 목적 유지도 | 개편 우세 | 온톨로지는 현 스키마의 확장 (§4) |
| 코드 재사용률 | 개편 우세 | ~85% (§7) |
| 성능 문제의 성격 | 개편 우세 | 설정·패턴 문제 — 재작성해도 재발, 개편으로 해소 (§2.3, §6.7) |
| 소규모 기관 운영 현실 | 개편 우세 | 비개발자 운영·수동 마이그레이션 관례에 신규 스택은 리스크만 추가 |
| 이용자 학습 부담 | 개편 우세 | 발달장애인 당사자에게 UI 전면 교체는 인지 접근성상 최대 리스크 — 점진 변화가 원칙 |
| 서비스 연속성 | 개편 우세 | 추가형 스키마로 무중단, Phase 단위 롤백 가능 vs 빅뱅 이관은 실패 시 복구 곤란 |

### 8.3 신규 제작을 다시 검토해야 하는 조건 (미래 트리거)

다음 조건이 현실화되면 그 시점에 재검토가 합리적입니다 — 현재는 해당 없음.
1. **다기관 SaaS 확장**: 여러 복지관이 한 인스턴스를 쓰는 멀티테넌시가 요구될 때 (현재는 기관별 개별 배포 모델).
2. **그래프 규모의 임계 초과**: 노드 수만 개 이상 + 상시 그래프 알고리즘(경로 탐색·군집)이 필요해질 때 → 그 시점에 그래프 DB 병행 재평가.
3. **공공 시스템 연동 의무화**: 행복e음 등과의 실시간 연동 규격이 확정되어 인증·감사 체계를 전면 재설계해야 할 때.

| 7 | **관계망 정보의 수집 범위·동의 절차** (개인정보 처리방침) | network_entities는 제3자(가족·이웃) 정보 — 수집 근거·동의 방식·보존 기한을 기관이 결정해야 스키마 확정 가능 | 4 |
| 8 | **AI 활용 고지·동의 현황** | 비식별화 게이트웨이 요건 확정(현재도 OCR로 영수증 이미지가 OpenAI에 전송됨) | 4 |

### 9.3 제도 자료 (지속 추적 필요)

- 보건복지부 **개인예산제 2026 본사업 지침 확정본** — 7단계 워크플로 명칭·서식의 최종 정합

사용법: [https://microsoft.github.io/Ontology-Playground/#/](https://microsoft.github.io/Ontology-Playground/#/) 접속 → JSON 파일 업로드 → 노드-엣지 다이어그램 자동 생성 → 사례관리자와 함께 누락 관계 점검(예: "이 목표는 이 자원과도 연결되어야 해요") → 합의 내용을 스키마 초안(부록 B)에 반영.
