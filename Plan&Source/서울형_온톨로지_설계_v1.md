## 1. 먼저, 지적하신 문제에 대해

> "지금 이 구조는 PCP, 개인예산제 어느 것도 아우르지 못하고 있는 것 같아."

맞습니다. 그리고 원인을 정확히 짚어야 다음 설계가 같은 실패를 반복하지 않습니다.

`pcp_ontology.rdf`는 **성격이 다른 두 종류의 지식을 한 모델에 넣었습니다.**

| | 서술적 지식 (descriptive) | 규범적 지식 (normative) |
|---|---|---|
| 무엇 | 이 사람은 어떤 사람인가 | 제도는 무엇을 허용하는가 |
| 예 | 가치·꿈·강점·관계망·To/For 균형 | 한도액·서비스영역·금지항목·심의절차 |
| 정답 | 사람마다 다름, 정답 없음 | 지침에 적혀 있음, 정답 있음 |
| 변화 | 사람이 변하면 변함 | 제도가 개정되면 변함 |
| 모델링 | 자유로운 그래프, 열린 어휘 | 코드값, CHECK 제약, 상태머신 |

두 지식을 하나로 합치면 **양쪽 다 어정쩡해집니다.**
서술적 부분에는 제약이 과하게 걸리고, 규범적 부분에는 제약이 모자랍니다.
31개 클래스짜리 통합 모델이 서울형에 안 맞았던 것은 크기 문제가 아니라 이 성격 충돌 때문입니다.

구체적으로, 서울형을 통합 모델에 넣으려 하면 이렇게 됩니다.

- 서울형 신청서의 **접수번호·중도장애 발생시기·공공부조 수급현황·복지부 중복참여 여부**가 착지할 곳이 없습니다.
- 서울형의 **개인정보 동의서**는 서식의 일부이고 참여의 전제인데, 통합 모델에는 동의 개념 자체가 없습니다.
- 반대로 통합 모델의 **SIS-A·4+1 평가·관계 지도·To/For 균형**은 서울형에 존재하지 않습니다. 빈 노드로 남습니다.
- 통합 모델은 서비스 영역을 `taxonomy + crosswalk`로 풀었지만, 서울형은 **6종이 제도로 확정**되어 있습니다. 매핑 계층이 불필요한 복잡도가 됩니다.

### 다만 한 가지는 다르게 제안드립니다

"보건복지부형, 서울형, 시범사업형 각각 DB를 설계한다"는 방향에 동의합니다.
**단, 사람은 나누지 않는 편이 좋겠습니다.**

세 DB를 완전히 분리하면 같은 사람이 세 번 등록되고, 한 사람이 복지부형에서 서울형으로 옮겨갈 때 이력이 끊기며,
"우리 기관 이용자 중 개인예산제 참여자는 몇 명인가" 같은 기본적인 질문에 답할 수 없게 됩니다.
실제로 `000 개별지원계획서` 사례가 이미 다중 재원(아산재단 92만원 + 기관예산 58만원)입니다.

그래서 이렇게 설계했습니다.

```
                    profiles / participants        ← 사람은 하나. 프로그램이 공유.
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
    seoul_*               mohw_*                 pcp_*
   서울형 모듈          복지부형 모듈          시범사업형 모듈
   (이번 산출물)           (다음)          (기존 pcp_ontology 이동)

   정형 · 코드값 중심     정형 · 코드값 중심     서술 · 열린 그래프
```

접두어로 완전히 격리되므로 서로를 건드리지 않습니다. 한 모듈을 갈아엎어도 다른 모듈은 무사합니다.
그러면서 사람은 한 명으로 유지됩니다.

## 2. 조사한 서울형 제도 파라미터

서식(`서울형 개인예산 양식.md`)은 **신청 단계까지만** 있어 운영 규칙을 별도로 조사했습니다.

| 항목 | 확인된 내용 |
|---|---|
| 지원 한도 | 1인 최대 **240만원** (월 최대 40만원 × 6개월). 2025년 월 40~50만원 |
| 대상 | 서울시 거주 만 18세 이상 **중증장애인** |
| 서비스 영역 | **6종** — 일상생활 / 사회생활 / 취·창업활동 / 자기개발 / 건강·안전 / 주거환경개선 |
| 지원 불가 | 주류·담배·복권 구입, 세금·공과금, 저축·부채상환 |
| 이용 요건 | 이용계획 포함, **장애 연관성**, **목표 연관성** |
| 절차 | 신청접수 → 참여자선정 → 계획수립 → 심의·통지 → **이의신청** → 서비스이용 → 모니터링·정산 (7단계) |
| 이의신청 | 접수 후 **14일** 이내 처리·재통보 ※ 아래 주의 참조 |
| 배제 규칙 | **복지부 시범사업 참여자는 서울형 참여 불가** (신청서에 명시) |
| 수행 구조 | 서울시 + 자치구 + 한국장애인재단 + 복지관 8곳 (동의서에 열거) |

> ⚠️ **14일 기준에 대한 주의.** 이 수치는 검색 결과에서 복지부형 지원위원회 설명과 함께 나왔습니다.
> 서울형에 동일하게 적용되는지, 기산점이 통지일인지 수령일인지는 **확인되지 않았습니다.**
> 그래서 상수로 박지 않고 `seoul_cohorts.appeal_due_days` 설정값으로 두었습니다.

출처는 §8에 정리했습니다.

## 3. 온톨로지 — 26 클래스 / 46 관계 / 94 속성

파일: `Plan&Source/ontology/seoul/seoul_ontology.rdf` (Ontology Playground 로드용 RDF/XML)

### 3.1 클래스 구성

| 군 | 클래스 | 근거 |
|---|---|---|
| 참여자·자격 (4) | `Participant` `Proxy` `DisabilityProfile` `BenefitStatus` | 신청서 인적사항 |
| 신청 (3) | `Application` `ConsentRecord` `SelectionDecision` | 신청서·동의서, 절차 ①② |
| 계획 (4) | `UtilizationPlan` `SelfNarrative` `RequestedService` `ServiceDomain` | 이용계획서, 절차 ③ |
| 심의·구제 (4) | `PlanReview` `ReviewCommittee` `Notification` `Appeal` | 절차 ④⑤ |
| 집행 (4) | `BudgetAllocation` `ServiceUsage` `Receipt` `ServiceProvider` | 절차 ⑥ |
| 통제·정산 (4) | `SpendingRule` `RuleCheck` `Settlement` `MonitoringRecord` | 절차 ⑦, 이용 제한 요건 |
| 기관 (3) | `AdministeringBody` `ExecutingAgency` `Caseworker` | 동의서 활용기관 목록 |

모든 클래스가 실제 서식 항목 또는 확인된 제도 규칙에서 나왔습니다. 추측으로 만든 클래스는 없습니다.

### 3.2 설계상 중요한 판단 다섯 가지

**① 계획의 저자는 참여자다**
`Participant -authors→ UtilizationPlan`. 3차 검토에서 통합 모델의 가장 큰 결함이
`Person → BudgetPlan` 관계 부재였던 것을 반복하지 않았습니다.
참여자에서 나가는 화살표는 8개 — 신청·동의·계획수립·이용·이의신청이 모두 당사자에서 출발합니다.
담당자는 `assists`(돕는다)이지 `creates`가 아닙니다.

**② 동의는 1급 개체다**
서식에 "동의 거부 시 사업 참여 불가"가 명시되어 있습니다. 부가정보가 아니라 참여의 전제이므로
별도 클래스로 두고, DB에서는 **동의 2건이 없으면 선정 자체가 불가능**하도록 트리거로 강제했습니다.
대리 서명 여부(`signedByProxy`)도 남깁니다 — 자기결정권이 핵심인 제도에서 누가 동의했는지가 사라지면 안 됩니다.

**③ 서술과 지출을 잇는 화살표를 하나 둔다**
`SelfNarrative -informs→ RequestedService`.
통합 모델의 `justifiesExpense`에 해당하는 자리입니다. "원하는 삶의 모습"과 "요청 서비스"가
이어지지 않으면 심의가 근거 없이 판단하게 됩니다.

**④ 통지를 별도 노드로 둔다**
이의신청은 심의가 아니라 **통지**를 대상으로 겁니다. 통지일이 기한의 기산점이기 때문입니다.
통지 없이 기한만 세면 권리구제가 형해화됩니다. `isReadByParticipant`까지 두었습니다 —
발송했다고 전달된 것은 아니고, 발달장애인 대상 사업이라면 확인 여부까지 봐야 합니다.

**⑤ 금지와 요건을 구분한다**
`SpendingRule.ruleKind`가 `prohibition`이면 시스템이 차단하고, `criterion`이면 플래그만 세웁니다.

> 3차 문서에서 저는 "자동 거절 없음"을 원칙으로 삼았습니다. 서울형에서는 그 원칙을 **부분적으로 뒤집습니다.**
> 주류·담배·복권은 제도가 명시적으로 금지한 것이라 차단이 맞습니다.
> 반면 "장애 연관성이 있는가"는 판단이므로 자동화하면 안 됩니다 —
> **말로 설명하기 어려운 당사자일수록 불리해지기 때문입니다.**
> 원칙이 바뀐 게 아니라, 프로그램마다 규칙의 성격이 달라서 적용이 달라진 것입니다.
> 이것 자체가 프로그램별 모듈 분리가 옳다는 근거이기도 합니다.

## 4. SQL 스키마 — 26 테이블 / 7 뷰 / 8 함수 / 5 트리거

파일: `Plan&Source/ontology/seoul/seoul_schema_draft.sql` (⚠️ 검토용 초안, 그대로 실행 금지)

### 4.1 설계 전제 세 가지

**① 제도 파라미터는 상수가 아니라 데이터**
240만원·40만원·6개월·14일을 코드에 박으면 3차 시범사업에서 전부 고쳐야 합니다.
`seoul_cohorts` 행으로 두어 차수마다 다르게 운영할 수 있게 했습니다.

**② 잔액은 저장하지 않는다**
1차 보고서에서 기존 앱의 잠복 결함으로 지적한 것이 **잔액 트리거 + 수동 보정 공존 → 이중 반영**이었습니다.
같은 실수를 반복하지 않기 위해 잔액은 항상 `v_seoul_budget_balance` 뷰에서 계산합니다.
느리면 인덱스를 걸지 값을 복제하지 않습니다 (`idx_seoul_usage_alloc_date`가 그 역할).

**③ 이중 한도를 함께 검사한다**
월 한도만 보면 총액을 넘고, 총액만 보면 한 달에 몰아 쓸 수 있습니다.
다만 **월 미사용액 이월 가능 여부가 확인되지 않아** `carry_over_allowed`로 분기했습니다.
기본값은 `TRUE`(총액만 강제)입니다 — 잘못 막으면 당사자가 즉시 손해를 보기 때문입니다.

### 4.2 강제되는 규칙 (트리거)

| 규칙 | 동작 |
|---|---|
| 복지부 중복 참여 | 선정 시도 시 **차단** |
| 동의 2건 미비 | 선정 시도 시 **차단** |
| 부결·조건부인데 사유 없음 | CHECK 제약으로 **차단** — 사유 없는 부결은 이의신청을 불가능하게 만든다 |
| 총 한도 초과 | **차단** |
| 월 한도 초과 (이월 불가 시) | **차단** |
| 이용일이 지원 기간 밖 | **차단** |
| 금지 항목 키워드 | **차단** + 근거 문구 표시 |
| 예산 배정 소유자 불일치 | **차단** |
| 계획에 없는 지출 | **통과 + 검토 플래그** (차단 아님) |
| 이의신청 기한 | 통지일 + 차수별 일수로 **자동 계산** |

### 4.3 주요 뷰

| 뷰 | 용도 |
|---|---|
| `v_seoul_budget_balance` | 잔액·소진액·계획외 건수 |
| `v_seoul_monthly_usage` | 월별 소진과 한도 초과 여부 |
| `v_seoul_unplanned_usages` | ⚠️ **물어볼 목록이지 거절 목록이 아님** |
| `v_seoul_appeal_status` | 이의신청 처리 기한 임박·도과 |
| `v_seoul_appealable_notifications` | 아직 이의신청 가능한 통지 (당사자 안내용) |
| `v_seoul_self_direction` | 주도성 지표 — **실무자 진단용, 당사자 화면에 비율로 표시 금지** |
| `v_seoul_pipeline` | 절차 진행 현황 한 줄 요약 |

## 5. 검증 — 실제 PostgreSQL 에서 실행했습니다

초안이지만 "문법이 맞을 것이다"로 끝내지 않고, **PostgreSQL 16 인스턴스를 띄워 실제로 실행하고 동작을 테스트**했습니다.
기존 `profiles`·`participants`·`auth.uid()`는 스텁으로 만들었습니다.

```
pglast (PostgreSQL 파서)  : 구문 파싱 통과
실제 실행                  : 26 테이블 · 7 뷰 · 8 함수 · 5 트리거 · 74 정책 · 14 인덱스 생성 성공
RLS 커버리지               : seoul_* 26개 테이블 전부 활성화, 정책 없는 테이블 0개
기능 테스트 T1~T13         : 13/13 통과
보안 테스트 S1~S15         : 15/15 통과
```

### 5.1 테스트가 잡아낸 결함 4건 (모두 수정 완료)

이 검증이 없었으면 그대로 넘어갔을 것들입니다.

**[치명] 참여자가 자기 예산 한도를 올릴 수 있었다**
`participant_id`를 가진 11개 테이블에 "본인이면 UPDATE 허용"을 일괄 적용한 것이 원인입니다.
실제로 총 한도를 **240만원 → 9,999만원**으로 바꾸는 데 성공했습니다.

**[치명] 참여자가 자기 이의신청 결과를 '인용'으로 바꿀 수 있었다**
같은 원인. 권리구제 절차 자체가 무의미해집니다.

**[치명] 참여자가 통지일을 2030년으로 옮겨 이의신청 기한을 무한 연장할 수 있었다**
같은 원인. 신청 상태를 스스로 `selected`로 바꾸는 것도 가능했습니다.

→ **원인과 교훈**: `participant_id`가 있다는 이유로 "본인 데이터 = 본인 수정 가능"으로 처리한 것이 잘못이었습니다.
**"본인에 관한 데이터"와 "본인이 쓰는 데이터"는 다릅니다.**

| | 예 | 참여자 권한 |
|---|---|---|
| 본인이 쓰는 것 | 이용계획(작성중) · 지출 기록 · 이의신청 제기 · 영수증 | **읽기 + 쓰기** |
| 본인에 관한 것 | 심의 결과 · 예산 배정 · 통지 · 선정 · 자격정보 · 이의신청 결과 | **읽기만** |

읽기는 반드시 열어야 합니다 — **자기 계획이 왜 부결됐는지 볼 수 없으면 이의신청을 할 수 없습니다.**
`seoul_is_staff_for()`를 `seoul_can_access()`와 별도로 만들어 이 경계를 구현했습니다.

**[중] 예산 소유권을 RLS 가시성에 의존하고 있었다**
A의 지출을 B의 예산에서 차감하는 시도는 막혔지만, 이유가 "RLS 때문에 B의 배정이 안 보여서"였습니다.
**두 참여자를 함께 담당하는 실무자에게는 양쪽이 모두 보이므로 통과했을 것입니다.**
트리거에 명시적 소유권 검사를 추가했습니다.

### 5.2 수정이 만든 회귀도 잡았습니다

RLS를 조인 뒤 **참여자가 계획에 없는 지출을 기록하면 지출 자체가 실패**하는 문제가 생겼습니다.
플래그를 남기는 트리거가 `SECURITY INVOKER`라 `seoul_rule_checks` 쓰기 정책에 걸린 것입니다.
플래그를 못 남긴다고 당사자의 기록을 막는 것은 앞뒤가 바뀐 것이므로 해당 트리거만 `SECURITY DEFINER`로 바꿨습니다.

## 5-1. 기존 Supabase 로도 온톨로지형 DB 가 되는가

**된다.** 다만 그래프 DB 를 따로 두는 방식이 아니라 **외래키를 트리플로 투영**하는 방식이다.
`seoul_graph_overlay.sql` 이 그 구현이고, 실제로 돌려서 확인했다.

### 왜 이 방식인가

핵심 관찰은 **외래키가 이미 엣지라는 것**이다.
`seoul_service_usages.requested_service_id` 컬럼은 "이 지출이 저 계획 항목을 이행한다"는
관계 그 자체다. 엣지 테이블을 따로 만들어 복제할 이유가 없다.

그래서 저장하지 않고 뷰로 파생시킨다(derived-first). 이중 쓰기가 없으니 표와 그래프가 어긋날 수 없다.

| | 네이티브 그래프 DB | 이 방식 (파생 오버레이) |
|---|---|---|
| Supabase 가능 여부 | **불가** — Apache AGE 미지원 | 가능 |
| 권한 | 별도 구현 + 동기화 | RLS 그대로 재사용 |
| 정합성 | 두 저장소 동기화 필요 | 트랜잭션 하나 |
| 운영 부담 | 저장소 2개 | 1개 |
| 질의 | Cypher/SPARQL | SQL 재귀 CTE |

Apache AGE 가 관리형 Supabase 에서 안 되는 이유는 Supabase 이미지가 Nix 로 빌드되어
런타임 확장 컴파일을 막아 두었기 때문이다. `pg_graphql` 은 지원되지만 이것은 **GraphQL API 계층이지
그래프 DB 가 아니다** — 이름 때문에 혼동하기 쉬운 지점이다.

### 실제로 되는 것

김민수(웹툰 작가가 되고 싶은 참여자) 사례로 검증했다.

```
엣지 50개 / 술어 31종이 외래키에서 자동 투영됨

경로 탐색 결과:
  3단계 | 계획을 세운다 → 서비스를 요청한다 → ← 계획 항목을 이행한다
        | 2025-01-15 드로잉 태블릿 구입 450,000원
```

그리고 이것이 온톨로지의 값어치다 — 표만 있으면 금액만 보이지만, 관계가 있으면 맥락이 보인다.

| 원하는 삶 | 순위 | 요청한 서비스 | 영역 | 예상 | 집행 | 상태 |
|---|---|---|---|---|---|---|
| 웹툰 작가가 되고 싶다 | 1 | 드로잉 태블릿 구입 | 자기개발 | 450,000 | 450,000 | 예상 범위 |
| 웹툰 작가가 되고 싶다 | 2 | 웹툰 아카데미 수강 | 자기개발 | 600,000 | 300,000 | 예상 범위 |
| 웹툰 작가가 되고 싶다 | 3 | 주 1회 수영 강습 | 건강·안전 | 300,000 | 150,000 | 예상 범위 |

"노트북을 샀다"가 아니라 "웹툰 작가가 되고 싶다 → 그림 배우기 → 태블릿 45만원"으로 읽힌다.
심의위원회가 판단할 때 필요한 것이 정확히 이 맥락이다.

### 돌려보고 알게 된 것 두 가지

**① 화살표는 거꾸로도 따라갈 수 있어야 한다**
"이 계획 항목에 돈이 얼마나 쓰였나"를 물으면 계획 → 지출로 가야 하는데,
`fulfills` 는 지출 → 계획 방향이라 정방향 탐색으로는 **0건**이 나왔다.
OWL 이라면 `owl:inverseOf` 로 선언할 것을 역방향 엣지 뷰로 만들어 해결했다.
같은 질문을 단방향으로 하면 여전히 0건, 양방향이면 12개 경로가 나온다.

**② [치명] PostgreSQL 뷰는 기본적으로 RLS 를 우회한다**
뷰는 기본값이 "뷰 소유자 권한으로 실행"이라, 소유자가 테이블 소유자면 하위 테이블의 RLS 가
통째로 무시된다. 초안에서 **무관한 참여자가 남의 엣지 50개를 전부 조회할 수 있었다.**

이건 그래프 오버레이만의 문제가 아니었다. **`seoul_schema_draft.sql` 의 잔액·정산·주도성 뷰 7개도
전부 같은 상태였다** — 즉 §5 에서 RLS 테스트를 통과했다고 한 것은 테이블 직접 접근에 한한 것이었고,
뷰를 경유하면 뚫렸다. 모든 뷰에 `WITH (security_invoker = true)` 를 붙여 해결했다(PostgreSQL 15 이상 필요).

> 여기서 얻은 교훈은 원칙으로 남길 만하다.
> **"RLS 를 걸었다"는 테이블에 건 것이지 뷰에 건 것이 아니다.**
> 뷰·함수·트리거 각각이 어떤 권한으로 실행되는지를 따로 확인해야 한다.
> 지금 운영 중인 앱의 기존 뷰들도 같은 점검이 필요하다.

부수적으로, 스텁에 RLS 를 채워 실제와 맞추자 `profiles` ↔ `participants` 정책이 서로를 조회해
**무한 재귀**가 났다. `SECURITY DEFINER` 헬퍼로 고리를 끊었다 — 실제 앱에서도 같은 패턴이 필요하다.

### 이 방식으로 안 되는 것 (정직하게)

1. **OWL 추론기가 없다.** 하위클래스 자동 상속 같은 추론은 직접 뷰로 써야 한다.
   실무 영향은 낮다 — 사례관리에서 필요한 것은 대개 추론이 아니라 경로 탐색이다.
2. **SPARQL 을 못 쓴다.** 다만 `seoul_export_triples()` 로 서브그래프를 트리플로 뽑을 수 있어,
   필요해지면 외부 도구로 내보내면 된다. 즉 **지금 그래프 DB 를 도입할 이유가 없다.**
3. **초대형 그래프는 전용 DB 가 빠르다.** 참여자 수십~수백 명 규모에서는 재귀 CTE 로 충분하다.

## 6. pcp 모델과 의도적으로 다르게 한 것

| | `pcp_ontology` | `seoul_ontology` |
|---|---|---|
| 서비스 분류 | taxonomy + crosswalk (기관마다 다름) | **코드 테이블 6종 고정** (제도 확정) |
| 규칙 | 전부 플래그, 자동 거절 없음 | **금지는 차단**, 요건은 플래그 |
| 서술 구조 | 열린 가치 노드 그래프 | **5칸 고정** (`SelfNarrative`) |
| 평가 | 4+1 · 성과 스냅샷 · 순환 고리 | **모니터링 기록** (서울형엔 정형 평가가 없음) |
| 관계망 | 관계 지도 4분면 | **없음** (서울형 서식에 없음) |
| 사정 도구 | SIS-A | **없음** |
| 동의 | 없음 | **1급 개체, 참여의 전제** |
| 심의 | 있음 (3차에서 추가) | 있음 + **통지·이의신청 기한 관리** |

없는 것을 억지로 넣지 않았습니다. 서울형에 관계 지도가 없는 것은 결함이 아니라 그 제도의 모습입니다.
기관이 PCP 실천을 함께 하고 싶다면 그것은 `pcp_*` 모듈에서 하고, 사람을 통해 이어집니다.
