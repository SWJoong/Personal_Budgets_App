# 22 · `/onboarding` 재연결 설계 메모 (D-20261003-04)

> **상태: 설계 초안** — 2026-10-03. 사용자가 「제거가 아니라 서울형 스키마에 맞게 재배선」을 선택했다(D-20261003-04). doc19 일정상 설계는 10/07~10/13(W), 구현은 결정 반영 구간(10/14~10/20)이다. 이 문서는 코드를 읽어서 규모와 선택지를 정리한 것이며 **코드·SQL 은 바꾸지 않는다**.
> **결론 먼저**: 지금 화면은 서울형에서 저장 단계가 깨져 있고, 서울형 모델에서는 「역할 고르기」와 「참여자 행 만들기」가 맞지 않는다. 그래서 **재연결 = 첫 로그인 때 이름·소개·사진을 확인하는 짧은 화면**으로 줄이는 것을 권한다. 완료 표시는 DB 컬럼을 새로 만들지 않는 방식(§4 B 또는 C)이 마감에 안전하다. 규모는 파일 3~4개 + 테스트 1개, `src/proxy.ts` 를 건드려 **high 티어**다.

## 2. 서울형 모델에서 온보딩이 해야 할 일

가입·역할·연결은 이미 시스템이 한다(초대·이메일 일치). 그래서 남는 일은 **첫 로그인 한 번**이다.

- 이름·한 줄 소개·사진을 확인·수정(구글 가입이면 이름·사진이 미리 채워짐)
- (당사자) 앱 쓰는 법을 쉬운 말로 짧게 안내 — 기존 `complete` 단계(당사자 가입 뒤에 나오는 마지막 단계)의 안내를 재사용할 수 있는지는 내용을 읽어 확인해야 한다(미확인)
- **하지 않는 것**: 역할 고르기, 참여자 행 만들기, 담당 실무자 직접 지정(실무자·관리자가 한다)

## 4. 「완료 표시」를 어디에 둘까 — 선택지

| | 방식 | 장점 | 단점·위험 | 필요한 작업 |
|---|---|---|---|---|
| **A** | `profiles.onboarding_completed` 컬럼을 서울형에 새로 추가 | 옛 코드와 가장 비슷 | **SQL 변경 = Manual-Ops + rls/auth 군 high 검증**, 기존 사용자를 **모두 완료(true)로 채우지 않으면 전원이 온보딩에 갇힘**(되돌리기 어려운 실수), 프록시의 매 요청 DB 조회가 계속 남음 | `01_core.sql`(+백필)·CI `db-verify`·대시보드 수동 반영 |
| **B** | 컬럼 없이 **이름이 비어 있으면 미완료**로 본다 | SQL·수동 작업 0, 기존 사용자는 이미 이름이 있어 안 갇힘 | 「한 번 봤는지」는 모름(이름이 미리 채워지면 화면 자체가 안 뜸 — 필요 없다면 괜찮음) | 프록시 판정 + 화면 |
| **C** | 로그인 계정의 사용자 메타데이터에 `onboarded` 표시 | SQL 0, **프록시가 DB 조회 없이 판정**(이미 가진 세션 정보) → 응답마다 DB 왕복 제거 | 메타데이터는 본인이 고칠 수 있음(보안 경계가 아닌 편의 표시라 괜찮음), 기존 사용자는 표시가 없어 **한 번 더 보게 됨**(미리 채우려면 관리자 API 로 계정마다 써야 해 번거롭다) | 프록시 판정 + 화면 + 기존 사용자 처리 규칙 |

**권고**: **B + C 조합** — 「이름이 비었거나 표시가 없는 **신규 계정**」만 온보딩으로 보내고, 기존 계정은 판정에서 제외한다(예: 계정 생성일이 배포일 이후일 때만). 이렇게 하면 SQL 이 없고(Manual-Ops 없음), 기존 사용자가 갇힐 위험이 없고, 프록시의 DB 조회를 없앨 수 있다. 단순함이 우선이면 **B 단독**.

## 6. 위험

- **갇힘 위험**(방식 A 한정): 백필을 빠뜨리면 기존 사용자가 모두 온보딩으로 간다. B·C 에서는 판정에서 기존 계정을 제외해 피한다.
- **권한 경계**: 화면이 역할을 바꾸지 못하게 해야 한다. 서울형의 역할 가드 트리거가 막아 주지만, 화면 코드도 `role` 쓰기를 없앤다.
- **당사자 대상 문구**: 새 안내 문구는 쉬운 말 기준(발달장애 당사자 노출 문구)으로 검수 필요 — 문구가 바뀌면 PR 템플릿 규칙상 high 선언.
- **마감 위험**: 이 항목은 마감 필수가 아니라 「가능하면」로 두었다(doc19 §4). 설계 후 규모가 권고안보다 커지면 필수/가능하면을 다시 정한다.

## 7. 사용자 결정이 필요한 것 (설계 확정 전, 10/13 까지)

1. **온보딩에서 무엇을 하게 할지**: ⓐ 이름·소개·사진 확인 + 쉬운 사용 안내(권고) ⓑ 이름·사진 확인만 ⓒ 그 밖의 항목(담당 실무자 안내 등)
2. **누가 보게 할지**: ⓐ 신규 계정 전원(권고) ⓑ 이름이 비어 있는 계정만
3. **완료 표시 방식**: ⓐ B+C 조합(권고) ⓑ B 단독 ⓒ A(SQL 필요 — Manual-Ops)
