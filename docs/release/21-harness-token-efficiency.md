## 1. 한눈에 보기

1. **돈이 새는 곳은 일의 양이 아니라 에이전트 수다.** 검증 에이전트 18개가 쓴 277만 토큰 중 **55%가 일을 시작하기도 전의 고정 부팅비**다(에이전트당 약 8.5만).
2. **결과가 없었던 검토에 절반을 썼다.** 최종적으로 남은 지적이 0건이었던 검토 3개가 전체의 **48%**(133만)를 썼다. 다만 「문제 없음」을 확인한 가치는 있으므로, 같은 확인을 더 싸게 할 수 있는지가 쟁점이다.
3. **같은 검증을 약 60~70% 적은 토큰으로 할 수 있다고 추정한다**(§4, 가정 명시). 진행 보고 품질은 오히려 올릴 수 있다(§5) — 보고는 단계가 바뀔 때 몇 줄이면 되어 토큰이 거의 들지 않는다.
4. **개선 1(재확인 묶기)을 PR #213 검증에서 실제로 시험했다**: 재확인 단계 **−43%**, 전체 **−25%**(§4 시험 결과). 다만 기각률이 낮아진 점은 품질 확인이 더 필요하다. 시험에 쓴 절차는 부록 B 에 있어 U 세션이 `verify-pr.js` 로 옮길 수 있다.

### 시험 결과 — 개선 1(재확인 묶기), 2026-10-03 PR #213 검증

같은 PR 에서 두 방식을 모두 돌린 것은 아니다. 새 방식(검토 3 + **묶음 재확인 2**)은 실제로 썼고, 이전 방식(검토 3 + 관점별 재확인 6)은 #209·#210 재확인 평균(약 13.8만)으로 추정했다.

| | 새 방식 (실측) | 이전 방식 (추정) |
|---|---|---|
| 에이전트 | 5 | 9 |
| 검토 3명 | 603,372 (202,715 · 199,412 · 201,245) | 같음 |
| 재확인 | **473,353** (2명: 231,459 · 241,894) | 약 828,000 (6명) |
| 합계 | **1,076,725** | 약 1,431,000 |

→ 재확인 단계 **−43%**, 전체 **−25%**.

읽는 법:
- 묶음 재확인자는 한 명당 23~24만으로, 이전 방식의 재확인자(약 12~16만)보다 크다. 지적 9건 전체를 보느라 도구 호출이 44~49회였다(이전 9~20회). 부팅비는 4명분(약 34만)을 아꼈지만 일의 양이 늘어서 절감폭이 부팅비 계산(−25~36%)의 아래쪽에 머물렀다.
- **품질 신호 — 아직 결론 못 냄**: ① 기각률이 낮아졌다. 묶음 재확인은 9건 중 3건만 기각(이전 #209 는 26건 중 21건 기각). 중복을 합쳐 지적이 더 구체적이었기 때문일 수도 있고, 목록 전체를 볼 때 덜 회의적이 되는 것일 수도 있다 — 같은 PR 을 두 방식으로 재실행한 비교가 필요하다. ② 2호에게 목록을 역순으로 보게 했을 때 1호와 6/9 가 일치했고 앞쪽 지적에 끌리는 편향의 뚜렷한 흔적은 없었다. ③ 의견이 갈린 것은 2/9(22%)로 이전 #209 의 35% 와 비슷하다.
- 이 PR 의 최종 판정은 조건부 승인(보통 1·낮음 5 생존)이었고, 검토 3명이 이미 같은 방향의 지적(SQL 요약 문장이 계약 밖)을 냈다.

## 5. 진행 보고 요구사항 (사용자 요청 2026-10-03)

> 요구: 진행도와 작업 흐름을 **사용자가 이해할 수 있는 수준의 자연어로**, 작업 흐름에 맞춰 알려줄 수 있게 하네싱한다.

현재 문제(이 세션에서 확인): 보고에 내부 용어(렌즈·반박자·생존·티어·게이트·계약)와 지적 번호(`dc2-1`)가 그대로 나온다. 사용자는 "지금 무엇이 끝났고 내가 뭘 해야 하는지"를 읽어내야 한다.

| 요구 | 설계안 | 토큰 영향 |
|---|---|---|
| R-1 단계가 바뀔 때 3줄 보고 | ① 지금 하는 일 ② 진행도(예: 검증 4단계 중 2단계) ③ 기다리는 것·막힌 것 ④ 사용자가 할 일(없으면 「없음」) | 단계당 약 100토큰 — 사실상 무료 |
| R-2 결론 먼저 | 최종 보고는 「판정 + 사용자가 결정할 것」을 첫 문단에, 세부는 아래에 | 0 |
| R-3 쉬운 말 사전 | 내부 용어 → 쉬운 말 대응표를 `harness:operate` 스킬에 두고 사용자에게 보이는 글에만 적용: 렌즈→「검토 관점」, 재검토자→「지적이 맞는지 다시 확인하는 검토자」, 생존→「재확인 후 남은 지적」, 티어→「검증 강도(가벼움·보통·엄격)」, 게이트→「머지 전 점검표」, Manual-Ops→「사용자가 직접 하는 수동 작업」, 계약→「먼저 만든 테스트」 | 스킬에 약 300토큰, 호출 시에만 |
| R-4 번호 대신 이름 | 지적은 ID 가 아니라 「문서 정합 지적 2건: …」처럼 내용으로 | 0 |
| R-5 에이전트 보고 맨 위 쉬운 요약 | 하위 에이전트 보고의 첫 3줄을 「쉬운 요약」으로 규정 → 오케스트레이터가 다시 읽지 않고 그대로 전달 | 보고 길이 상한과 함께 토큰 절감 |

## 부록 B · 이번에 쓴 가벼운 검증 절차 (수동 팬아웃) — `verify-pr.js` 로 옮길 때 참고

고위험(high) PR 을 검증할 때 #213 에서 쓴 순서다. 이전 방식과 다른 점은 3·4 단계다.

1. **범위 파악** (오케스트레이터): PR 번호·head·변경 파일·CI·선언 티어.
2. **검토** (`harness:w-verifier`, 병렬, 고위험 PR 은 3관점): 문서 일관성 · 테스트·변이 · 요구 충실도·게이트 안전. 프롬프트에 넣을 것 — 대상·head·변경 파일 / 규칙(코드·문서 수정 금지, 변이는 격리 worktree 와 node_modules junction 에서만, 끝나면 원복·제거) / 관점별 점검 항목 / **출력 형식: 맨 위 쉬운 요약 3줄 → 지적(`[심각도] 한글 제목 @ 위치 — 증거 — 이유 — 제안`) → 확인한 것**.
3. **지적 합치기** (오케스트레이터): 세 보고의 지적을 중복 제거해 번호 목록(F1…)으로 만든다. 이번에는 12건 → 9건이었고, 지적자가 「조치 불필요」로 판정한 1건은 뺐다.
4. **묶음 재확인** (`sonnet` 2명): **전체 목록**을 각자 독립적으로 판단한다(2호는 역순으로 보게 해 앞쪽에 끌리는 편향을 줄임). 한 줄에 한 건 `Fn | refuted=true|false | 근거`. 규칙 — 확인 못 하면 `true` + 「미확인」, 이 PR 이 만든 문제인지 PR 이전부터 있던 것인지 구분, 심각도가 맞는지 판단.
5. **집계**: 치명·높음은 재확인자 1명이라도 확인하면 남기고, 보통·낮음은 2명 모두 확인해야 남긴다. 판정 — 치명·높음 남음 → 수정 요구 / 보통만 → 조건부 승인 / 낮음만·없음 → 승인.
6. **리포트 첨부**: `pr-merge-gate.sh N attach --verdict … --source manual-fanout --tier high`(헤더 자동 생성). head 가 바뀌면 지적이 남았던 관점만 `--lens` 로 재검증.

Windows 주의: 검증자 Bash 명령에 `push` 글자가 들어가면 `merge-ask` 훅이 오탐 차단하므로 텍스트 검색은 Grep 도구를 쓴다. `jq.exe` 가 줄 끝에 CR 을 붙여 `pr-risk-tier.sh` 가 틀리게 계산하므로 `jq -b` 래퍼나 `tr -d '\r'` 가 필요하다(doc18 §9 플러그인 0.4.2 후속).
